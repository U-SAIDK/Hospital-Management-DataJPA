# JPQL vs Native Queries

## 1. Definition

`@Query` lets a repository method carry an explicit query instead of relying on the method name. It
comes in two flavours: **JPQL** — an object-oriented query language that operates on *entity and
field names* (`Patient`, `p.bloodGroup`) which Hibernate translates to SQL — and **native SQL**
(`nativeQuery = true`) — raw SQL run against the actual *table and column names* (`patient`), bypassing
JPQL translation entirely.

## 2. Core Idea

Use JPQL when the query is about your object model (it stays portable across databases and reuses
your mappings, including `@Enumerated`). Drop to native SQL only when you need database-specific
syntax or something JPQL can't express. `@Query` also unlocks three things derived methods can't do
cleanly: **constructor-expression DTO projections**, **bulk `@Modifying` DML**, and explicit
**`JOIN FETCH`** for N+1 control.

## 3. Why We Need It

Derived method names top out fast (see `04. Query Methods`). Once a query filters on an enum, computes
an aggregate, projects into a DTO, issues a bulk UPDATE, or needs a fetch join, the name-as-query
approach either becomes unreadable or simply can't express it. `@Query` covers all of those while
keeping the query text next to the method that uses it.

## 4. Internal Working

- **JPQL** — Hibernate parses the JPQL string against the entity metamodel, then compiles it to SQL
  using the entity's column/table mappings. Field references and enum values are resolved through the
  same mappings the entities declare (so `p.bloodGroup = ?1` compares against the STRING encoding).
- **Positional (`?1`) vs named (`:birthDate`) binding** — `?1` binds by parameter position; `:name`
  binds by `@Param("name")`. Named binding is reorder-safe.
- **Constructor expression** — `SELECT new <FQN>(…)` tells Hibernate to instantiate the named class
  per result row by calling a constructor whose parameter types/order match the select list exactly.
  This is resolved at query-*execution* time, not compile time.
- **Native query** — the string is sent to the DB almost verbatim; Hibernate still maps the result
  set back to the entity (when the return type is an entity) and, for `Page`/`Pageable`, appends
  `LIMIT/OFFSET` and issues a separate `COUNT` query.
- **`@Modifying`** — marks the `@Query` as DML (UPDATE/DELETE) so Spring Data calls
  `executeUpdate()` instead of a select, and returns the affected-row count. It runs as a *bulk*
  statement straight against the DB, skipping the persistence context.
- **`JOIN FETCH`** — instructs Hibernate to initialise the joined association *in the same select*,
  so the association is populated without a second query.

## 6. Real-world Analogy

JPQL is ordering from a menu written in *your restaurant's* item names ("the Patient special, blood
group O") — the kitchen knows how to translate that to actual ingredients (SQL). Native SQL is
walking into the kitchen and writing the recipe yourself in raw ingredient terms — more power, but you
lose the menu's abstraction and portability. A constructor-expression projection is asking for a
pre-plated combo (`BloodGroupCountResponseEntity`) instead of a tray of raw ingredients (`Object[]`)
you'd have to assemble at the table.

## 7. How THIS PROJECT Uses It

All examples live in `repository/PatientRepository.java`, exercised by `service/PatientService.java`:

- **JPQL, positional bind** — `findByBloodGroup` (`?1`, filters on the enum field `p.bloodGroup`).
- **JPQL, named bind** — `findByBornAfterDate` (`:birthDate` via `@Param`).
- **JPQL constructor-expression / DTO projection** — `countEachBloodGroupType`, projecting into
  `dto/BloodGroupCountResponseEntity.java`; the commented-out `List<Object[]>` variant is left as a
  "before" contrast.
- **Native query with pagination** — `findAllPatients` (`select * from patient`, `nativeQuery=true`,
  returns `Page<Patient>`), called by `PatientService.getAllPatients` with `PageRequest.of(...)`.
- **`@Modifying` + `@Transactional` bulk update** — `updateNameWithId`.
- **`JOIN FETCH`** — `findAllPatientWithAppointment` (`LEFT JOIN FETCH p.appointments`), with a
  commented-out deeper double-fetch variant flagged as a `MultipleBagFetchException` risk.

## 9. Line-by-Line Explanation

- `@Query("SELECT p FROM Patient p where p.bloodGroup = ?1")` — JPQL, so `Patient` is the *entity*
  name and `p.bloodGroup` the *field*, not the table/column. `?1` binds the first parameter
  positionally. Because `bloodGroup` is `@Enumerated(STRING)`, Hibernate compares against the stored
  enum name. (The `@Param("bloodGroup")` here is inert since the query uses positional `?1`.)
- `@Query("select p from Patient p where p.birthDate > :birthDate")` — named binding: `:birthDate`
  resolves via `@Param("birthDate")`. Named params are order-independent and self-documenting, which
  is why they're preferred once a query has more than one parameter.
- `select new com.codingshuttle...BloodGroupCountResponseEntity(p.bloodGroup, Count(p)) … group by
  p.bloodGroup` — a **constructor expression**. Hibernate calls
  `new BloodGroupCountResponseEntity(BloodGroupType, Long)` for each grouped row. The class must be
  named by its **fully-qualified name**, and the constructor's parameter order/types must match the
  select list `(BloodGroupType, Long)` *exactly*. `BloodGroupCountResponseEntity` supplies that via
  `@AllArgsConstructor(bloodGroupType, count)`. None of this is compile-checked — a mismatch throws
  only when the query executes. The commented `List<Object[]>` line is the untyped "before" version.
- `@Query(value = "select * from patient", nativeQuery = true)` returning `Page<Patient>` — raw SQL
  against the `patient` table. Even though it's native, Spring Data appends `LIMIT/OFFSET` from the
  `Pageable` and runs a second `COUNT(*)` query to populate the `Page` metadata. `PatientService`
  passes `PageRequest.of(pageNumber, pageSize)`.
- `@Transactional @Modifying @Query("UPDATE Patient p SET p.name = :name where p.id = :id")` — a
  **bulk UPDATE**. `@Modifying` makes Spring Data call `executeUpdate()` (returning the affected-row
  `int`); `@Transactional` is required because DML must run in a transaction. Critically this bypasses
  the persistence context: **no `Patient` is loaded, dirty checking and entity listeners never run,
  and any `Patient` already managed in the same context for that id becomes stale until refreshed** —
  the deliberate opposite of the dirty-checking path in `AppointmentService`.
- `@Query("SELECT p FROM Patient p LEFT JOIN FETCH p.appointments")` — `JOIN FETCH` loads each
  `Patient` *and* its `appointments` in one SQL join, avoiding the N+1 pattern of loading patients
  then hitting the DB once per patient for appointments. `LEFT` keeps patients with zero appointments.
  The commented variant adds a second fetch (`a.doctor`); chaining two collection fetch-joins is what
  can trigger Hibernate's `MultipleBagFetchException`, so it's left commented as a caution.

## 10. Common Mistakes

- **Writing table/column names in JPQL.** `SELECT * FROM patient` is *not* valid JPQL — JPQL needs
  `SELECT p FROM Patient p`. Table names belong only in native queries (`findAllPatients`).
- **Breaking a constructor expression silently.** Reordering `BloodGroupCountResponseEntity`'s
  constructor or changing a field type compiles fine but throws at query execution, because the JPQL
  string references the constructor by shape, not type-checked reference.
- **Expecting a bulk `@Modifying` update to refresh loaded entities.** After `updateNameWithId`, an
  already-loaded `Patient` still shows the old name until reloaded — a classic staleness trap.
- **Forgetting `@Modifying` or `@Transactional` on a DML `@Query`.** Without `@Modifying` Spring Data
  treats it as a select and fails; without a transaction the update can't execute.
- **Stacking multiple collection `JOIN FETCH`es.** Two `LEFT JOIN FETCH` over bag collections risks
  `MultipleBagFetchException` and a Cartesian row explosion — the reason the deeper variant here stays
  commented.

## 11. Best Practices

- Prefer JPQL over native SQL unless you truly need DB-specific features — JPQL stays portable and
  reuses entity mappings (including `@Enumerated(STRING)`).
- Use named parameters (`:birthDate`) over positional (`?1`) once there's more than one, as
  `findByBornAfterDate` does — resilient to reordering and self-documenting.
- Project to a DTO with a constructor expression when you only need a few columns/aggregates
  (`countEachBloodGroupType`) instead of loading full entities — less data over the wire and the
  aggregate has no home on the entity.
- Keep bulk `@Modifying` updates for genuine set-based writes, and be aware they skip the persistence
  context; reload affected entities if the same context keeps using them.
- Use `JOIN FETCH` deliberately to kill N+1, but fetch at most one collection per query.

## 12. Performance Notes

- **Constructor projection** (`countEachBloodGroupType`) only pulls the grouped columns
  (`bloodGroup`, count) over the wire instead of hydrating every `Patient` — cheaper both in transfer
  and in entity-mapping overhead.
- **`findAllPatients`** issues two statements per call (the paged select + a `COUNT`) because the
  return type is `Page`; that's the cost of knowing the total element count.
- **Bulk `@Modifying`** (`updateNameWithId`) updates rows in a single statement with no per-entity
  load/flush — far cheaper than loading a `Patient`, mutating, and letting dirty checking write it,
  at the cost of persistence-context consistency.
- **`JOIN FETCH`** (`findAllPatientWithAppointment`) collapses N+1 into one query; but a collection
  fetch-join can return duplicate parent rows (one per child), which is why such queries often need
  `DISTINCT`, and why stacking two collection fetches is discouraged.

## 13. Interview Questions

- Q: JPQL vs native query — what's the core difference?
  A: JPQL operates on entity/field names and is DB-portable (Hibernate compiles it to SQL); native
  queries are raw SQL on table/column names, used only when you need DB-specific behaviour.
- Q: What must line up for a constructor-expression projection to work?
  A: The fully-qualified class name in the query, plus a constructor whose parameter order and types
  exactly match the select list — validated only at query execution, not compile time.
- Q: Why does a `@Modifying` bulk update risk stale data?
  A: It runs straight against the DB without loading entities, so it never triggers dirty checking or
  updates entities already managed in the current persistence context.
- Q: Does pagination work with native queries?
  A: Yes — with a `Pageable` param and a `Page` return, Spring Data appends `LIMIT/OFFSET` and issues
  a separate `COUNT`, as `findAllPatients` shows.
- Q: How does `JOIN FETCH` fix N+1, and what's its risk?
  A: It loads the association in the same select instead of one query per parent; the risk is
  duplicate parent rows and `MultipleBagFetchException` when fetching more than one collection.

## 14. Summary

`@Query` picks up where derived methods stop. In `PatientRepository`, JPQL handles enum filtering
(`findByBloodGroup`, positional) and date ranges (`findByBornAfterDate`, named); a constructor
expression projects grouped counts into `BloodGroupCountResponseEntity` (exact constructor match
required, checked only at runtime); a native query (`findAllPatients`) still paginates through a
`Pageable`; a `@Modifying` + `@Transactional` bulk `updateNameWithId` writes directly to the DB and
bypasses dirty checking (leaving loaded entities stale); and `findAllPatientWithAppointment` uses
`LEFT JOIN FETCH` to defeat N+1 — with the commented deeper fetch flagged as a
`MultipleBagFetchException` hazard.
