# Project Walkthrough — End-to-End Tours

This document traces five real request flows through the actual files, controller → service →
repository → entity, so you can see how the pieces documented separately (entities, security,
transactions, DTOs) fit together at runtime. It is intentionally a *tour*, not a spec. For the
per-step mechanics it points at rather than re-derives:

- `src/MASTER_NOTES.md` §4 — the canonical request lifecycle (create-appointment) walked in detail.
- `src/MASTER_NOTES.md` §5 — transaction/dirty-checking lifecycle.
- `src/MASTER_NOTES.md` §8 — the security flow (JWT + OAuth2).
- The numbered `NOTES/0X` concept files for any single concept (fetching, DTOs, etc.).

All paths are under `src/main/java/com/codingshuttle/youtube/hospitalManagement/` unless noted.
Base context path is `/api/v1` (see `application.properties`), so every URL below is prefixed with it.

## Flow 1 — Email/password signup

**Entry:** `POST /api/v1/auth/signup` — public (see `WebSecurityConfig`).

```
AuthController.signup(SignUpRequestDto)          controller/AuthController.java
        │  ResponseEntity.ok(authService.signup(dto))
        ▼
AuthService.signup(dto)                           security/AuthService.java
        │  → signUpInternal(dto, AuthProviderType.EMAIL, null)
        ▼
AuthService.signUpInternal(dto, EMAIL, null)
        │  1. userRepository.findByUsername(username) → if present, throw IllegalArgumentException
        │  2. User.builder()... (username, providerId=null, providerType=EMAIL, roles from dto)
        │  3. EMAIL provider → user.setPassword(passwordEncoder.encode(dto.getPassword()))   (BCrypt)
        │  4. userRepository.save(user)
        │  5. Patient.builder().name(...).email(username).user(user).build()
        │  6. patientRepository.save(patient)
        │  → returns the saved User
        ▼
AuthService.signup wraps it: new SignupResponseDto(user.getId(), user.getUsername())
```

**What to notice:**
- `signUpInternal` is the **shared core** for both plain signup and OAuth2 signup — the two flows can
  never diverge on *how* a `User`+`Patient` pair is created; only `providerType`/`providerId`/password
  differ per caller.
- **Every self-service signup becomes a `Patient`.** A `User` row is never created without its
  `Patient` counterpart. Doctors are *only* created via admin onboarding (Flow 5).
- `SignUpRequestDto.roles` exists as a request field, but in practice the account is a Patient
  regardless — a real gap worth *noticing*, not fixing (documentation-only scope).
- The response is deliberately minimal — `id` + `username`, **no JWT**. Signup and login are separate
  steps here (contrast `LoginResponseDto`, which carries the token). See `NOTES/15` on why these DTO
  shapes are deliberate.

## Flow 2a — Login (JWT issuance)

**Entry:** `POST /api/v1/auth/login` — public.

```
AuthController.login(LoginRequestDto)             controller/AuthController.java
        ▼
AuthService.login(dto)                            security/AuthService.java
        │  authenticationManager.authenticate(
        │       new UsernamePasswordAuthenticationToken(username, password))
        ▼
Spring Security's AuthenticationManager (bean from config/AppConfig.java)
        │  delegates to DaoAuthenticationProvider, which:
        │    - CustomUserDetailsService.loadUserByUsername(username)   security/CustomUserDetailsService.java
        │          → userRepository.findByUsername(username).orElseThrow()
        │    - checks password with the BCrypt PasswordEncoder bean (AppConfig)
        ▼
authentication.getPrincipal()  →  cast straight to User   (User implements UserDetails — no adapter)
        │
        ▼
authUtil.generateAccessToken(user)                security/AuthUtil.java
        │  Jwts.builder().subject(username).claim("userId", id)
        │       .issuedAt(now).expiration(now + 10 min).signWith(HMAC key from jwt.secretKey).compact()
        ▼
return new LoginResponseDto(token, user.getId())
```

**What to notice:**
- The `AuthenticationManager` is exposed as a bean in `AppConfig` purely so `AuthService` can call
  `authenticate(...)` directly instead of wiring a `DaoAuthenticationProvider` by hand.
- **The principal cast is a bare `(User)`** — because `entity/User.java implements UserDetails`, the
  JPA entity *is* the security principal; there is no separate UserDetails DTO/adapter to translate.
  `CustomUserDetailsService.loadUserByUsername` literally returns the `User` entity.
- The JWT is **HMAC-signed, 10-minute expiry, no refresh token** (`AuthUtil.generateAccessToken`) — a
  short-lived access token by design; the client re-logs-in when it expires.
- On every subsequent request, `JwtAuthFilter` re-reads this token and rebuilds the
  `SecurityContext` — see `MASTER_NOTES.md` §4/§8; not repeated here.

## Flow 2b — OAuth2 login (Google/GitHub)

**Entry:** Spring Security's built-in `oauth2Login()` filter chain (configured in `WebSecurityConfig`,
provider registrations in `application.yml`). The provider redirect/callback is handled by Spring
Security itself; the app-specific logic starts at the success handler.

```
(provider redirect + callback handled by Spring Security's oauth2Login filter)
        ▼
OAuth2SuccessHandler.onAuthenticationSuccess(req, res, authentication)   security/OAuth2SuccessHandler.java
        │  token = (OAuth2AuthenticationToken) authentication
        │  oAuth2User = (OAuth2User) authentication.getPrincipal()
        │  registrationId = token.getAuthorizedClientRegistrationId()   ("google" / "github")
        ▼
AuthService.handleOAuth2LoginRequest(oAuth2User, registrationId)   security/AuthService.java  (@Transactional)
        │  1. providerType = authUtil.getProviderTypeFromRegistrationId(registrationId)
        │  2. providerId  = authUtil.determineProviderIdFromOAuth2User(...)   (Google: "sub", GitHub: "id")
        │  3. user   = userRepository.findByProviderIdAndProviderType(providerId, providerType)
        │     emailUser = userRepository.findByUsername(email)
        │  4a. user == null && emailUser == null  → SIGNUP:
        │         username = authUtil.determineUsernameFromOAuth2User(...)
        │         signUpInternal(new SignUpRequestDto(username, null, name, Set.of(RoleType.PATIENT)),
        │                        providerType, providerId)          ← SAME core as Flow 1, no password
        │  4b. user != null → optionally sync username to a changed email, userRepository.save(user)
        │  4c. else (email already registered on another provider) → throw BadCredentialsException
        │  5. return ResponseEntity.ok(new LoginResponseDto(authUtil.generateAccessToken(user), user.getId()))
        ▼
OAuth2SuccessHandler writes the LoginResponseDto JSON DIRECTLY to HttpServletResponse
        (response.setStatus / setContentType(JSON) / getWriter().write(objectMapper.writeValueAsString(...)))
```

**What to notice:**
- OAuth2 login ends with the **exact same `LoginResponseDto` (JWT) contract** as plain login — clients
  never need to know which flow issued the token (`LoginResponseDto`'s own comment says as much).
- The success handler writes the response **by hand** to the raw `HttpServletResponse` because it runs
  *inside Spring Security's OAuth2 filter*, not a `@Controller` — there is no DispatcherServlet/MVC
  pipeline around it to shape the JSON.
- Provider differences are isolated in `AuthUtil`: Google's stable id is the `sub` attribute, GitHub's
  is a numeric `id`; username falls back email → provider handle (`login`) → raw `providerId` so signup
  can never fail on a missing username.
- New OAuth2 users go through the *same* `signUpInternal` as Flow 1 (User+Patient together), just with
  a real `providerId` and no password.

## Flow 3 — Create an appointment (and reassign it)

**Entry:** `POST /api/v1/patients/appointments` — authenticated.

This is the flow `MASTER_NOTES.md` §4 walks step-by-step; here is the condensed map — see §4 for the
full request-lifecycle narration (filter → security → controller → service → mapper).

```
PatientController.createNewAppointment(CreateAppointmentRequestDto)   controller/PatientController.java
        ▼
AppointmentService.createNewAppointment(dto)   service/AppointmentService.java
        │  @Transactional, @Secured("ROLE_PATIENT")
        │  1. patient = patientRepository.findById(patientId).orElseThrow(EntityNotFoundException)
        │  2. doctor  = doctorRepository.findById(doctorId).orElseThrow(EntityNotFoundException)
        │  3. Appointment.builder().reason(...).appointmentTime(...).build()   (transient)
        │  4. appointment.setPatient(patient); appointment.setDoctor(doctor)   ← FK-owning side (persisted)
        │  5. patient.getAppointments().add(appointment)                       ← in-memory consistency only
        │  6. appointment = appointmentRepository.save(appointment)            → EntityManager.persist → INSERT
        │  7. return modelMapper.map(appointment, AppointmentResponseDto.class)
```

**What to notice:**
- Only the **FK-owning side** (`appointment.patient`/`.doctor`) controls what is written. The
  `patient.getAppointments().add(...)` line changes nothing in the DB — it just keeps the in-memory
  object graph consistent for the rest of this persistence context. (Same pattern in reassign, below.)
- Entities never leave the service — step 7 maps to `AppointmentResponseDto` so lazy/EAGER associations
  never reach Jackson. See `NOTES/15`.

**Reassignment** (the canonical **dirty-checking** example — full mechanics in `MASTER_NOTES.md` §5):

```
AppointmentService.reAssignAppointmentToAnotherDoctor(appointmentId, doctorId)
        │  @Transactional
        │  @PreAuthorize("hasAuthority('appointment:write') or #doctorId == authentication.principal.id")
        │  1. appointment = appointmentRepository.findById(appointmentId).orElseThrow()   → MANAGED entity
        │  2. doctor      = doctorRepository.findById(doctorId).orElseThrow()
        │  3. appointment.setDoctor(doctor)      ← NO explicit save()
        │  4. doctor.getAppointments().add(appointment)   ← in-memory consistency only
        │  → at transaction commit, Hibernate's dirty checking detects the changed doctor and issues UPDATE
```

- **No `save()` call.** Because `appointment` was loaded via `findById` inside an active
  `@Transactional` method, it is a *managed* entity; Hibernate compares its state to the load-time
  snapshot at commit, sees `doctor` changed, and emits the UPDATE automatically. This is *the* place in
  the codebase to observe dirty checking (pair with `show-sql=true`).
- The `@PreAuthorize` SpEL lets a doctor reassign only their **own** appointments unless they hold the
  coarser `appointment:write` authority (e.g. admin) — finer-grained than any URL rule can express.

## Flow 4 — Admin onboards a doctor

**Entry:** `POST /api/v1/admin/onBoardNewDoctor` — the whole `/admin/**` prefix is gated to
`ROLE_ADMIN` in `WebSecurityConfig`. This is the **only** path in the codebase that creates a `Doctor`
row (every other account defaults to `Patient` via `signUpInternal`, Flows 1/2b).

```
AdminController.onBoardNewDoctor(OnboardDoctorRequestDto)   controller/AdminController.java
        ▼
DoctorService.onBoardNewDoctor(dto)   service/DoctorService.java   (@Transactional)
        │  1. user = userRepository.findById(dto.getUserId()).orElseThrow()     ← User must already exist
        │  2. if doctorRepository.existsById(userId) → throw IllegalArgumentException("Already a doctor")
        │        (existsById works on the User's id because Doctor's PK IS the User's id via @MapsId)
        │  3. Doctor.builder().name(...).specialization(...).user(user).build()
        │  4. user.getRoles().add(RoleType.DOCTOR)   ← dirty checking: user is managed, no save() needed
        │  5. return modelMapper.map(doctorRepository.save(doctor), DoctorResponseDto.class)
```

**What to notice:**
- The target `User` must already exist (created via normal signup first) — reflecting the shared-PK
  (`@MapsId`) design: a `Doctor` row can only attach to an existing `User` id, so `OnboardDoctorRequestDto`
  carries a `userId`, not full user details.
- **Two mutations, one transaction:** creating the `Doctor` row *and* elevating the `User`'s roles must
  succeed or fail together — a `User` marked `DOCTOR` without a `Doctor` row (or vice versa) would be
  inconsistent. That's why `@Transactional` matters here.
- The role change (`user.getRoles().add(RoleType.DOCTOR)`) needs **no explicit `userRepository.save()`**
  — `user` is still managed from the `findById` in the same transaction, so dirty checking persists it
  at flush (same mechanism as Flow 3's reassign).
- `RoleType.DOCTOR` in `user.roles` is what later makes `getAuthorities()` grant the DOCTOR authorities
  (`User.getAuthorities()` expands roles via `RolePermissionMapping`) — so this one onboarding step is
  what unlocks the doctor-only endpoints for that user on future logins.
