# Persistence Context

## 1. Definition

The **persistence context** is the in-memory area, managed by an `EntityManager` (backed in this
project by a Hibernate `Session`), that holds every entity instance Hibernate currently "knows
about" during a unit of work. It is simultaneously three things: a **first-level cache** (an
identity map keyed by entity type + primary key), a **change tracker** (it remembers what each
managed entity looked like when it was loaded, so it can detect modifications), and the **scope
boundary** that decides when lazy associations can still be initialized. In this codebase, one
persistence context is created per `@Transactional` service method and torn down when that method
commits.

## 2. Core Idea

You never talk to the database row directly — you talk to a Java object that the persistence
context has *bound* to that row. As long as that binding is alive (the context is open), Hibernate
gives you three guarantees:

- **Identity** — ask for `Patient` id 4 twice in the same context and you get the *same* Java object
  instance, not two copies (identity map / deduplicated SELECTs).
- **Automatic write-back** — mutate a managed object's fields and Hibernate will schedule the
  matching UPDATE at flush time, with no explicit `save()` call (dirty checking).
- **Deferred, batched SQL** — writes are queued and flushed together (usually at commit), in an
  order Hibernate chooses to satisfy FK constraints.

The persistence context is the single mechanism that makes all three possible.

## 3. Why We Need It

Without a persistence context, JPA would be a thin wrapper over JDBC: every read is a fresh SELECT,
every change needs an explicit UPDATE, and the same row loaded twice becomes two divergent objects
that can silently overwrite each other. The persistence context solves exactly those problems:

- It **deduplicates reads** within a unit of work, so bidirectional navigation (`appointment`
  → `doctor` → back to that same `appointment`) doesn't fan out into repeated queries.
- It lets service code express intent as **plain object mutation** (`appointment.setDoctor(doctor)`)
  instead of hand-written SQL — see `AppointmentService.reAssignAppointmentToAnotherDoctor`.
- It gives a **consistent flush point** so that a group of related changes hit the database
  together and can be rolled back together.

## 4. Internal Working

For each managed entity, the context stores two things: the **entity instance** you hold a
reference to, and a **snapshot** — a copy of the entity's persistent field values taken at the
moment it entered the context (via `findById`/`save`). Structurally it is roughly an
`IdentityMap<EntityKey, EntityEntry>` where `EntityKey = (entity class, primary key)`.

Lifecycle of one `@Transactional` method:

1. **Open** — on method entry Spring's transaction interceptor starts a transaction and binds a new
   Hibernate `Session` (the persistence context) to the current thread.
2. **Load** — `repository.findById(id)` first checks the identity map. On a miss it issues a SELECT
   and stores `(instance, snapshot)`. On a hit it returns the already-present instance with **no
   SQL** (this is the dedup / first-level cache).
3. **Mutate** — your setters change the instance but not the snapshot.
4. **Flush** — before commit (or when Hibernate needs to), it walks every managed entity, compares
   current field values against the snapshot, and for each difference emits an UPDATE. New entities
   emit INSERT; orphaned/removed ones emit DELETE.
5. **Commit + close** — SQL is committed and the context is discarded. Every entity it held is now
   **detached**; its snapshot is gone, so further mutations are no longer tracked.

Because this project registers **no explicit `OpenEntityManagerInViewFilter` override** anywhere in
`src/` (confirmed by searching the codebase), the practical scope you can rely on for tracked writes
and safe lazy access is the body of the `@Transactional` method itself — once it returns, the
context that method used is done.

## 5. Flow Diagram (ASCII)

```
 @Transactional reAssignAppointmentToAnotherDoctor(appointmentId, doctorId)
        │
        │  (1) tx begins → new Hibernate Session (persistence context) opens
        ▼
 findById(appointmentId) ─── miss ──► SELECT appointment ──► store {instance, SNAPSHOT_A}
        │
 findById(doctorId)      ─── miss ──► SELECT doctor      ──► store {instance, SNAPSHOT_D}
        │
        ▼
 appointment.setDoctor(doctor)     (instance changes; SNAPSHOT_A unchanged)
        │
        ▼
 method returns → tx commit
        │
        │  FLUSH: compare each managed entity to its snapshot
        │   appointment.doctor differs from SNAPSHOT_A  ──► UPDATE appointment SET doctor_id=?
        ▼
 context closes → appointment & doctor become DETACHED
```

## 6. Real-world Analogy

Think of a hospital **whiteboard for the current shift**. When a patient's chart is pulled, a card
goes on the board with a photocopy of the chart as it looked when pulled (the snapshot). Staff
scribble changes on the live card all shift. Nobody runs to the records room per change. At the
**end of the shift** (commit), a clerk compares each live card to its photocopy and files only the
differences into the permanent record. Pull the same patient's chart twice during the shift and you
get the *same* card — not two — so two nurses can't unknowingly keep divergent versions. When the
shift ends the board is wiped; a card you kept in your pocket afterward (a detached entity) is just
a dead photocopy — writing on it changes nothing.

## 7. How THIS PROJECT Uses It

Every service method that mutates entities relies on the persistence context being open for its
whole body:

- `AppointmentService.reAssignAppointmentToAnotherDoctor` (`service/AppointmentService.java`) — the
  cleanest demonstration: two `findById` calls populate the context, one setter mutates a managed
  entity, and the UPDATE is emitted at flush **with no `save()` call**. (Deep-dived in
  `NOTES/09. Dirty Checking.md`.)
- `AppointmentService.createNewAppointment` — the `Patient` and `Doctor` loaded here stay managed
  through the `save(appointment)` and the `patient.getAppointments().add(appointment)` bookkeeping,
  so the whole object graph is consistent within one context.
- `DoctorService.onBoardNewDoctor` (`service/DoctorService.java`) — loads a `User`, then
  `user.getRoles().add(RoleType.DOCTOR)` is persisted purely because `user` is still managed in this
  context; there is no `userRepository.save(user)`.
- `InsuranceService.disaccociateInsuranceFromPatient` (`service/InsuranceService.java`) — nulling a
  field on the managed `patient` is enough for the context to detect an orphan and schedule a DELETE.
- `PatientService.getPatientById` (`service/PatientService.java`) — `@Transactional` deliberately
  keeps the context open through the `modelMapper.map(...)` call so any lazy association ModelMapper
  might touch can still be initialized before the context closes.

The identity-map / dedup behavior is why bidirectional-consistency lines like
`doctor.getAppointments().add(appointment)` are safe: the `appointment` added is the very same
managed instance already tracked, not a second copy.

## 8. Code Example From This Project

```java
// service/AppointmentService.java
@Transactional
@PreAuthorize("hasAuthority('appointment:write') or #doctorId == authentication.principal.id")
public Appointment reAssignAppointmentToAnotherDoctor(Long appointmentId, Long doctorId) {
    Appointment appointment = appointmentRepository.findById(appointmentId).orElseThrow();
    Doctor doctor = doctorRepository.findById(doctorId).orElseThrow();

    appointment.setDoctor(doctor); // this will automatically call the update, because it is dirty

    doctor.getAppointments().add(appointment); // just for bidirectional consistency

    return appointment;
}
```

## 9. Line-by-Line Explanation

- `@Transactional` — opens the transaction and the persistence context that this whole method runs
  inside; without it there is no context to keep `appointment` managed, and the setter below would
  never produce an UPDATE.
- `appointmentRepository.findById(appointmentId)` — issues a SELECT (on a first load) and registers
  `appointment` in the identity map together with a snapshot of its loaded state. A second
  `findById(appointmentId)` in this same method would return this exact instance with no SQL.
- `doctorRepository.findById(doctorId)` — same registration for `doctor`; it too is now managed.
- `appointment.setDoctor(doctor)` — mutates the managed instance. The snapshot is untouched, so at
  flush the context sees `doctor_id` changed and schedules exactly one UPDATE.
- `doctor.getAppointments().add(appointment)` — pure in-memory graph upkeep. Because `appointment`
  is the *same* managed instance the context already holds, this list now correctly reflects reality
  for anyone re-reading it in this context; it does **not** cause a separate write (the FK lives on
  `Appointment`, the owning side).
- `return appointment` — returns a still-managed entity. It stays managed only until this method
  commits; after that it is detached (relevant to `NOTES/08. Entity Lifecycle.md`).

## 10. Common Mistakes

- **Expecting caching across methods.** The first-level cache lives and dies with one persistence
  context. `getPatientById` loading `Patient` 4 does not spare a *different* request's method from
  re-SELECTing it — the context is per transaction, not application-wide.
- **Accessing a lazy field after the context closed.** `Appointment.doctor` is LAZY; touching it on
  an entity returned from a `@Transactional` method, after commit, throws
  `LazyInitializationException` because the context that could initialize the proxy is gone.
- **Assuming a bulk `@Modifying` update refreshes the context.** `PatientRepository.updateNameWithId`
  writes straight to the DB and never touches the identity map, so a `Patient` already loaded in the
  current context keeps its old name until reloaded.
- **Thinking `save()` is what persists changes to a managed entity.** For a managed entity, the
  *context* persists changes at flush; calling `save()` on it is redundant.

## 11. Best Practices

- Do all mutation of an entity **inside** the `@Transactional` boundary that loaded it, then map to
  a DTO before returning — the pattern used by `createNewAppointment`, `getPatientById`, and
  `getAllAppointmentsOfDoctor`.
- Convert entities to DTOs (`modelMapper.map(...)`) while the context is still open, so no lazy
  access happens after it closes.
- Keep transactions short: the context holds a snapshot per loaded entity, so loading thousands of
  entities into one context costs memory and lengthens the dirty-check scan at flush.
- Rely on the identity map instead of caching entities yourself in fields or static maps — those
  copies escape the context and go stale.

## 12. Performance Notes

- **Dedup SELECTs** — the identity map means repeated `findById` for the same key in one context is
  free after the first hit, and it prevents the "same row loaded as two objects" hazard.
- **Dirty-check cost** — flush scans *every* managed entity and diffs it field-by-field against its
  snapshot. A context bloated with entities you only read (never modify) still pays that scan; keep
  read-heavy paths lean or map straight to DTO projections (e.g.
  `PatientRepository.countEachBloodGroupType`) that never enter the context as managed entities.
- **Batching** — because writes are queued until flush, related INSERT/UPDATE/DELETE statements go
  out together at commit rather than one network round-trip per setter.

## 13. Interview Questions

- **Q: What is the persistence context and how is it different from a second-level cache?**
  A: It is the per-unit-of-work first-level cache + change tracker owned by one `EntityManager`/
  `Session`; it is not shared between transactions. A second-level cache (not configured in this
  project) is shared across contexts.
- **Q: Why can you update an entity without calling `save()`?**
  A: Because a managed entity's changes are detected by comparing it to the snapshot the context
  took at load; the UPDATE is emitted at flush. See `reAssignAppointmentToAnotherDoctor`.
- **Q: What determines the persistence context's scope in this app?**
  A: The `@Transactional` method boundary — there is no `OpenEntityManagerInViewFilter` override in
  the code, so the context you can rely on for tracked writes and lazy access is that method's body.
- **Q: If you load the same entity id twice in one transaction, how many SELECTs run?**
  A: One — the second call is served from the identity map.

## 14. Summary

The persistence context is Hibernate's per-transaction workspace: an identity map that dedups reads,
a snapshot store that powers dirty checking, and the scope inside which lazy associations can still
load. In this project it is created per `@Transactional` service method and closed at commit, with
no OSIV override extending it. `reAssignAppointmentToAnotherDoctor` shows all of it at once — load,
mutate a managed entity, and let flush emit the UPDATE — while entities returned past the method
boundary become detached and can no longer be tracked or lazily initialized.
