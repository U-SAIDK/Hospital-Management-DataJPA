# Transactions in Spring Data JPA

## 1. Definition

A **transaction** is an all-or-nothing unit of database work: every statement inside it either
commits together or rolls back together, so the database never sees a half-finished change. In
Spring, `@Transactional` on a method declares that boundary — Spring's proxy begins a transaction
before the method runs and commits it after the method returns (or rolls back if a runtime exception
propagates). In this project the annotation used is `jakarta.transaction.Transactional` (the JTA
annotation), which Spring's transaction infrastructure recognizes and drives with its own
`JpaTransactionManager`.

## 2. Core Idea

`@Transactional` does two jobs at once here:

1. **Atomicity** — a group of writes (e.g. create a `Doctor` *and* elevate a `User`'s roles)
   succeeds or fails as a whole.
2. **A persistence-context window** — the transaction opens a Hibernate `Session` and keeps loaded
   entities *managed* for the method's duration, which is precisely what enables dirty checking,
   cascade/orphanRemoval, and safe lazy access.

So in this codebase, `@Transactional` is placed on methods that mutate multiple entities together or
that need the persistence context to stay open across a mapping/lazy access.

## 3. Why We Need It

Without a transaction boundary, each repository call runs in its own auto-committed unit:

- Multi-step mutations lose atomicity — a failure between two saves leaves inconsistent data.
- Entities detach immediately after each read, so dirty checking and lazy loading can't work across
  statements.
- Cascade/orphanRemoval effects that depend on a shared flush point don't compose.

`@Transactional` gives all the statements in a method one shared connection, one persistence context,
and one commit/rollback decision.

## 4. Internal Working

- **Proxy interception.** `@Service` beans are wrapped by a Spring AOP proxy. Calling a
  `@Transactional` method goes through `TransactionInterceptor`, which asks the
  `PlatformTransactionManager` (here `JpaTransactionManager`) to begin a transaction and bind a
  Hibernate `Session` to the thread.
- **Propagation = REQUIRED (default).** If a transaction is already active on the thread, the method
  joins it; otherwise a new one starts. This is why `AuthService.handleOAuth2LoginRequest`
  (`@Transactional`) calling `signUpInternal` runs the inner saves inside the *same* transaction —
  they join the caller's.
- **Commit / rollback.** On normal return the interceptor commits (triggering Hibernate's flush). If
  an unchecked exception propagates, it rolls back. (By default Spring rolls back on
  `RuntimeException`/`Error`; the JTA `jakarta.transaction.Transactional` default also rolls back on
  unchecked exceptions.)
- **Why on the service, not the repository or controller.** Spring Data repository methods are each
  individually transactional, but business *use cases* span several repository calls plus entity
  mutations — that whole use case is the correct atomic unit, and it lives in the `@Service`. Putting
  it on the controller would drag request-mapping/serialization concerns into the transaction and
  extend the persistence context over view rendering; putting it only on the repository would make
  each call its own transaction and lose cross-call atomicity and shared dirty checking.

`jakarta.transaction.Transactional` vs `org.springframework.transaction.annotation.Transactional`:
Spring understands both. The JTA annotation is treated as an alias for Spring's own for proxying
purposes, driven by the same `JpaTransactionManager`. The main difference is a smaller feature set
(e.g. no `readOnly`, a different rollback-rules API) — functionally, in this app, it opens and closes
transactions exactly as Spring's annotation would.

## 5. Flow Diagram (ASCII)

```
 Controller (no @Transactional)
     │  call
     ▼
 ┌───────────────────────────────────────────────┐
 │ Spring AOP proxy around @Service               │
 │   TransactionInterceptor.begin()  ── tx START ─┼──► Session (persistence context) opens
 │      │                                          │
 │      ▼                                          │
 │   service method body                           │
 │      findById(), setters, save() ...            │  (entities MANAGED here)
 │      │                                          │
 │      ▼                                          │
 │   normal return ───────────────► commit ───────┼──► FLUSH (dirty checks, cascades) + COMMIT
 │   runtime exception ───────────► rollback ──────┼──► discard all pending SQL
 └───────────────────────────────────────────────┘
                                                    Session closes → entities DETACH
```

## 6. Real-world Analogy

A **bank transfer** at a teller window. Debiting one account and crediting another must both happen
or neither — the teller opens a single transaction, does both entries, and commits only when both
succeed; if the second fails, the first is undone. The window (the service method) is where the whole
transfer is coordinated, not the individual ledger books (repositories) and not the customer at the
door (controller). "Propagation REQUIRED" is like a supervisor who joins the transfer already in
progress rather than opening a second, conflicting one.

## 7. How THIS PROJECT Uses It

Every `@Transactional` in the codebase, and why it's there:

- **`AppointmentService.createNewAppointment`** (`service/AppointmentService.java`) — keeps `Patient`
  and `Doctor` managed while the new `Appointment` is built, wired, and saved atomically in one
  context.
- **`AppointmentService.reAssignAppointmentToAnotherDoctor`** — the dirty-checking case; the tx keeps
  `appointment` managed so the doctor change flushes as an UPDATE with no `save()`.
- **`DoctorService.onBoardNewDoctor`** (`service/DoctorService.java`) — mutates *two* things (creates
  a `Doctor`, adds `RoleType.DOCTOR` to the `User`) that must succeed or fail together; the User's
  role change persists via dirty checking within this tx.
- **`InsuranceService.assignInsuranceToPatient`** (`service/InsuranceService.java`) — sets the owning
  side on a managed `Patient`; cascade=ALL inserts the new `Insurance` within this tx.
- **`InsuranceService.disaccociateInsuranceFromPatient`** — nulls `patient.insurance`; orphanRemoval
  schedules the `Insurance` DELETE at this tx's flush.
- **`PatientService.getPatientById`** (`service/PatientService.java`) — read-only, but
  `@Transactional` deliberately keeps the context open through `modelMapper.map(...)` so any lazy
  association it might touch can still initialize.
- **`AuthService.handleOAuth2LoginRequest`** (`security/AuthService.java`) — may perform a `User` save
  **and** a `Patient` save (through `signUpInternal`) as one atomic OAuth2 signup.
- **`PatientRepository.updateNameWithId`** (`repository/PatientRepository.java`) — `@Transactional`
  is *required* on this method because it is a `@Modifying` bulk UPDATE, and Spring Data mandates an
  active transaction for DML `@Query` methods.

Methods deliberately **not** `@Transactional`, and the consequence:

- **`DoctorService.getAllDoctors`** — a single read + in-context DTO mapping; no multi-step atomicity
  needed.
- **`PatientService.getAllPatients`** — a native paged query returning a `Page` directly; no lazy
  access, so no open context required.
- **`AuthService.signUpInternal`** — **has no `@Transactional` of its own.** When reached through
  `AuthService.handleOAuth2LoginRequest` it inherits that caller's transaction (propagation REQUIRED)
  and is atomic. But when reached through the plain `AuthService.signup()` path (`signup()` →
  `signUpInternal()`), **there is no surrounding transaction at all**, so the `userRepository.save(user)`
  and the subsequent `patientRepository.save(patient)` run as two *separate* auto-committed
  operations. That means the plain email/password signup path is **not atomic**: if the `Patient`
  save fails, the already-committed `User` row remains. This is a real, observable property of the
  current code (stated factually here, not "fixed").

## 8. Code Example From This Project

```java
// service/DoctorService.java
@Transactional
public DoctorResponseDto onBoardNewDoctor(OnboardDoctorRequestDto onBoardDoctorRequestDto) {
    User user = userRepository.findById(onBoardDoctorRequestDto.getUserId()).orElseThrow();

    if(doctorRepository.existsById(onBoardDoctorRequestDto.getUserId())) {
        throw new IllegalArgumentException("Already a doctor");
    }

    Doctor doctor = Doctor.builder()
            .name(onBoardDoctorRequestDto.getName())
            .specialization(onBoardDoctorRequestDto.getSpecialization())
            .user(user)
            .build();

    // User is already managed (loaded via findById in this same @Transactional method), so this
    // role change is persisted by dirty checking at flush time - no explicit userRepository.save().
    user.getRoles().add(RoleType.DOCTOR);

    return modelMapper.map(doctorRepository.save(doctor), DoctorResponseDto.class);
}
```

And the non-atomic plain-signup path to contrast:

```java
// security/AuthService.java  (signUpInternal has NO @Transactional)
public User signUpInternal(SignUpRequestDto signupRequestDto, AuthProviderType authProviderType, String providerId) {
    // ...
    user = userRepository.save(user);         // committed on its own when called from signup()
    // ...
    patientRepository.save(patient);          // separate commit — not atomic with the User save
    return user;
}

public SignupResponseDto signup(SignUpRequestDto signupRequestDto) {
    User user = signUpInternal(signupRequestDto, AuthProviderType.EMAIL, null); // no tx around this
    return new SignupResponseDto(user.getId(), user.getUsername());
}
```

## 9. Line-by-Line Explanation

- `@Transactional` on `onBoardNewDoctor` — begins the tx and opens the context; both the `User` load
  and the `Doctor` save share it.
- `userRepository.findById(...).orElseThrow()` — returns a **managed** `User`; its later role change
  will be tracked.
- `existsById(...)` guard — a business rule executed inside the tx; throwing here rolls back
  cleanly (nothing was written yet anyway).
- `user.getRoles().add(RoleType.DOCTOR)` — mutates the managed `User`; persisted by dirty checking at
  flush, **no `userRepository.save`** — this only works because the tx keeps `user` managed.
- `doctorRepository.save(doctor)` — INSERTs the new `Doctor`; committed atomically with the role
  change when the method returns.
- In `signUpInternal`, `userRepository.save(user)` then `patientRepository.save(patient)` — with no
  `@Transactional` on the `signup()` path, each is its own commit, so a failure between them leaves an
  orphaned `User`.

## 10. Common Mistakes

- **Assuming every service method is atomic.** `signUpInternal` via `signup()` is not — the two saves
  aren't in one transaction.
- **Self-invocation bypassing the proxy.** If a bean called its own `@Transactional` method via
  `this.method()`, the proxy is skipped and no transaction starts. (Here the tx methods are entered
  from other beans/controllers, so this isn't triggered — but it's the classic trap.)
- **Putting `@Transactional` on the controller.** It would stretch the persistence context across
  serialization and blur the atomic unit; this project keeps it on services.
- **Forgetting `@Transactional` on a `@Modifying` query.** Spring Data requires it for DML — which is
  exactly why `updateNameWithId` carries it.
- **Expecting rollback on a checked exception by default.** Default rollback is on unchecked
  exceptions; a checked exception would (by default) commit.

## 11. Best Practices

- Put `@Transactional` at the **service** layer, on the method that represents one business use case
  — the pattern this project follows.
- Make read-only-but-lazy-touching methods transactional (like `getPatientById`) so mapping happens
  with the context open; leave pure, self-contained reads (`getAllDoctors`, `getAllPatients`)
  non-transactional.
- Group writes that must be consistent into one transactional method (e.g. `onBoardNewDoctor`); be
  aware where that grouping is *missing* (the plain signup path) and treat it as a known gap.
- Keep transactions short and free of remote/slow calls so connections and the persistence context
  aren't held open unnecessarily.

## 12. Performance Notes

- A transaction holds one DB connection for its duration; long methods keep connections checked out
  of the pool — keep them tight.
- One transaction = one flush = statements batched at commit, which is cheaper than many
  auto-committed round trips (an incidental cost of the non-transactional plain-signup path: two
  commits instead of one).
- `@Modifying` bulk updates like `updateNameWithId` are the most efficient way to change many rows —
  one statement, no per-entity loading — at the cost of bypassing the context (see
  `NOTES/09. Dirty Checking.md`).
- Marking genuinely read-only transactions as read-only (available with Spring's own annotation, not
  the JTA one used here) can let Hibernate skip dirty-check bookkeeping — a possible optimization not
  currently applied in this project.

## 13. Interview Questions

- **Q: What does `@Transactional` actually start, and where does the boundary live?**
  A: The Spring AOP proxy begins a transaction (via `JpaTransactionManager`) and opens a Hibernate
  Session before the method; commit/flush or rollback happens as it returns. It's placed on the
  service.
- **Q: Why does `handleOAuth2LoginRequest` make `signUpInternal` atomic but `signup()` does not?**
  A: `handleOAuth2LoginRequest` is `@Transactional`, so `signUpInternal` joins its transaction
  (propagation REQUIRED); `signup()` is not transactional, so the two saves inside `signUpInternal`
  auto-commit separately.
- **Q: Does `jakarta.transaction.Transactional` work with Spring's transaction management?**
  A: Yes — Spring recognizes the JTA annotation as an alias for its own and drives it with the same
  transaction manager; it just exposes fewer options (no `readOnly`, different rollback rules).
- **Q: Why must a `@Modifying` query be `@Transactional`?**
  A: It executes DML, which Spring Data requires to run inside an active transaction — hence the
  annotation on `updateNameWithId`.

## 14. Summary

`@Transactional` (here the JTA `jakarta.transaction.Transactional`, driven by Spring's
`JpaTransactionManager`) marks the atomic unit of work and opens the persistence context that makes
dirty checking, cascades, and lazy loading possible. This project puts it on service methods that
mutate multiple entities together — `createNewAppointment`, `reAssignAppointmentToAnotherDoctor`,
`onBoardNewDoctor`, both `InsuranceService` methods, `getPatientById`, `handleOAuth2LoginRequest` —
plus the `@Modifying` `updateNameWithId` where Spring Data requires it. The notable real gap:
`signUpInternal` has no `@Transactional` of its own, so the plain `signup()` path saves `User` and
`Patient` in two separate commits and is not atomic.
