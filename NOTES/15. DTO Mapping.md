# DTO Mapping

## 1. Definition

A **DTO (Data Transfer Object)** is a plain, association-free object whose only job is to carry data
across a boundary — here, the HTTP API boundary between the service layer and the JSON on the wire.
Entities (`Patient`, `Doctor`, `Appointment`, `User`) model the *database*; DTOs
(`PatientResponseDto`, `DoctorResponseDto`, `AppointmentResponseDto`, ...) model the *API contract*.
Mapping is the act of converting one to the other. This project does that mapping two different ways:
**ModelMapper** (reflection, after the entity is fetched) and **JPQL constructor expressions**
(the DTO is built *by the query itself*).

## 2. Core Idea

```
                         two ways to produce a DTO
   ┌───────────────────────────────────────────────────────────────┐
   │  A) fetch entity → modelMapper.map(entity, XDto.class)         │  post-fetch reflection
   │       used in PatientService / DoctorService / AppointmentService
   │                                                                 │
   │  B) SELECT new ...Dto(col, agg) FROM Entity ...                 │  DTO built in the query
   │       used in PatientRepository.countEachBloodGroupType         │
   └───────────────────────────────────────────────────────────────┘
```

- **Approach A** hydrates the full entity, then copies matching fields into a DTO by name.
- **Approach B** never hydrates an entity at all — Hibernate constructs the DTO directly from the
  `SELECT` list. Ideal for aggregates that have no home on an entity.

## 3. Why We Need It

Returning entities straight to Jackson is a trap for four concrete reasons visible in this codebase:

1. **Lazy proxies leak.** `Appointment.doctor` is `@ManyToOne(fetch = LAZY)`. Serializing an
   `Appointment` entity outside the persistence context would trip `LazyInitializationException` (or
   force an extra query). `AppointmentResponseDto` sidesteps this.
2. **Security-sensitive fields leak.** `Doctor`/`Patient` share a PK with `User` (`@MapsId`), and
   `User` holds `password` and `roles`. A DTO exposes only `id/name/specialization/email`, never the
   `User`.
3. **Over-fetching / accidental graph serialization.** `Patient.appointments` is `EAGER`; returning
   the entity would serialize the whole appointments collection (and the owned `Insurance`) on every
   response, even a "just the demographics" endpoint. `PatientResponseDto` omits both.
4. **Wire-contract stability.** The DTO shape can stay fixed even as the entity/schema evolves — the
   API is decoupled from the table.

## 4. Internal Working

**Approach A — ModelMapper (reflection, post-fetch).** `config/AppConfig.java` defines a single bean:

```java
// config/AppConfig.java
@Bean
public ModelMapper modelMapper() {
    return new ModelMapper();
}
```

At each call site the service fetches a managed entity, then `modelMapper.map(entity, XDto.class)`
walks the DTO's fields by name and copies matching entity properties in via reflection. It's
convention-based: `PatientResponseDto.name` is filled from `Patient.name`, `bloodGroup` from
`bloodGroup`, etc. Fields the DTO doesn't declare (like `appointments`) are simply never touched.

Call sites (all `modelMapper.map(...)`):
- `PatientService.getPatientById` / `getAllPatients` → `PatientResponseDto`
- `AppointmentService.createNewAppointment` / `getAllAppointmentsOfDoctor` → `AppointmentResponseDto`
- `DoctorService.getAllDoctors` / `onBoardNewDoctor` → `DoctorResponseDto`

**Approach B — JPQL constructor expression (query-built DTO).**
`PatientRepository.countEachBloodGroupType` builds the DTO in the query:

```java
// repository/PatientRepository.java
@Query("select new com.codingshuttle.youtube.hospitalManagement.dto.BloodGroupCountResponseEntity(p.bloodGroup," +
        " Count(p)) from Patient p group by p.bloodGroup")
List<BloodGroupCountResponseEntity> countEachBloodGroupType();
```

Hibernate calls `new BloodGroupCountResponseEntity(bloodGroup, count)` for each result row directly —
no `Patient` entity is ever instantiated. This requires the DTO to have a constructor whose
**parameter order and types exactly match** the `SELECT new(...)` argument list:

```java
// dto/BloodGroupCountResponseEntity.java
@AllArgsConstructor
public class BloodGroupCountResponseEntity {
    private BloodGroupType bloodGroupType;   // ← p.bloodGroup
    private Long count;                       // ← Count(p)
}
```

## 5. Flow Diagram (ASCII)

```
── Approach A: ModelMapper ─────────────────────────────────
repository.findById(id) ─► Patient (full entity, managed)
        │
        ▼  modelMapper.map(patient, PatientResponseDto.class)   (reflection, field-by-name)
   PatientResponseDto { id, name, gender, birthDate, bloodGroup }   ← no insurance/appointments/User
        │
        ▼
      JSON

── Approach B: JPQL constructor expression ─────────────────
"select new ...BloodGroupCountResponseEntity(p.bloodGroup, Count(p)) ... group by p.bloodGroup"
        │  (Hibernate calls the constructor per row — no Patient entity built)
        ▼
   List<BloodGroupCountResponseEntity> { bloodGroupType, count }
```

## 6. Real-world Analogy

An entity is your full employee file — salary, home address, performance notes. A DTO is the badge
you print from it: name and photo only. Approach A is printing the badge *after* pulling the whole
file (you fetched everything, then copied a subset). Approach B is asking HR "just give me a
head-count per department" — they never pull anyone's file, they hand you a tally sheet built to spec.
For a tally, pulling every file (Approach A) would be wasteful; for a badge of one known person,
pulling the file you already have open (Approach A) is fine.

## 7. How THIS PROJECT Uses It

Every response DTO in `dto/` and its role:

- **`PatientResponseDto`** (`id, name, gender, birthDate, bloodGroup`) — omits `insurance`,
  `appointments`, and the shared `User`/security fields. Built by ModelMapper in `PatientService`.
- **`DoctorResponseDto`** (`id, name, specialization, email`) — flattens away the `User` shared-PK
  pair and the `departments`/`appointments` collections. Built by ModelMapper in `DoctorService`.
- **`AppointmentResponseDto`** (`id, appointmentTime, reason, doctor: DoctorResponseDto`) — nests a
  `DoctorResponseDto`; the `patient` field is present in source but **commented out** deliberately
  (used from doctor-facing endpoints where echoing the patient back is redundant). Built by
  ModelMapper in `AppointmentService`.
- **`CreateAppointmentRequestDto`** (`doctorId, patientId, appointmentTime, reason`) — *inbound*;
  carries raw ids, not entity refs, so request parsing is decoupled from association loading.
- **`SignUpRequestDto`, `SignupResponseDto`, `LoginRequestDto`, `LoginResponseDto`,
  `OnboardDoctorRequestDto`** — inbound/outbound auth & admin shapes (mapped by hand in the security
  layer, not via ModelMapper — e.g. `new SignupResponseDto(user.getId(), user.getUsername())`).
- **`BloodGroupCountResponseEntity`** (`bloodGroupType, count`) — the **query-built** DTO (Approach B),
  the odd one out: not produced by ModelMapper but by the JPQL constructor expression.

## 8. Code Example From This Project

```java
// service/AppointmentService.java — Approach A (ModelMapper, post-fetch)
appointment = appointmentRepository.save(appointment);
return modelMapper.map(appointment, AppointmentResponseDto.class);
```

```java
// dto/AppointmentResponseDto.java — the shape is a deliberate contract choice
@Data
public class AppointmentResponseDto {
    private Long id;
    private LocalDateTime appointmentTime;
    private String reason;
    private DoctorResponseDto doctor;
    // patient is commented out deliberately: doctor-facing endpoints already know the patient.
//    private PatientResponseDto patient;
}
```

```java
// repository/PatientRepository.java — Approach B (JPQL constructor expression)
@Query("select new com.codingshuttle.youtube.hospitalManagement.dto.BloodGroupCountResponseEntity(p.bloodGroup," +
```

## 9. Line-by-Line Explanation

- `modelMapper.map(appointment, AppointmentResponseDto.class)` — reflection copies `id`,
  `appointmentTime`, `reason`, and (recursively) `doctor` into a new `AppointmentResponseDto`. The
  commented-out `patient` field is never populated because it isn't declared — the DTO's field list
  *is* the contract.
- The commented `// private PatientResponseDto patient;` — a concrete example that DTO shape is a
  design decision, not a 1:1 mirror of the entity. The entity always has a `patient`; the DTO chooses
  not to expose it here.
- `select new com.codingshuttle...BloodGroupCountResponseEntity(p.bloodGroup, Count(p))` — the
  **fully-qualified** class name is mandatory in a JPQL constructor expression. `p.bloodGroup` and
  `Count(p)` must line up positionally with the constructor's `(BloodGroupType, Long)` parameters.
- `@AllArgsConstructor` on `BloodGroupCountResponseEntity` — this is the constructor the query calls.
  Reorder its fields, rename them, or change a type, and the JPQL string breaks **silently** (it isn't
  compile-time checked against the constructor) — the repo's own comment warns about exactly this.
- `group by p.bloodGroup` + `Count(p)` — an aggregate that has no natural field on `Patient`; Approach
  B is the right tool precisely because there's no entity to map from.

## 10. Common Mistakes

- **Returning the entity directly.** Would leak `User.password`/`roles` (via the shared PK), serialize
  `Patient.appointments` (EAGER) and `Insurance` on every call, and risk `LazyInitializationException`
  on `Appointment.doctor` (LAZY). The DTOs exist specifically to prevent all of this.
- **Assuming the DTO must mirror the entity 1:1.** `AppointmentResponseDto` deliberately drops
  `patient`; `DoctorResponseDto` deliberately drops `departments`/`appointments`. The DTO is a
  contract, chosen field by field.
- **Breaking the constructor-expression silently.** Reordering/renaming/retyping
  `BloodGroupCountResponseEntity`'s fields breaks `countEachBloodGroupType`'s JPQL with no compile
  error — it fails only at query execution.
- **Using ModelMapper for an aggregate.** You can't `modelMapper.map` your way to a `COUNT(*)` grouped
  result — there's no source entity. That's the case Approach B exists for.
- **Trusting ModelMapper's name-matching blindly.** It matches by property name via reflection;
  mismatched or ambiguously-named fields map wrong (or not at all) and surface only at **runtime**, not
  compile time — the cost of the convenience.

## 11. Best Practices

- **Always map to a DTO at the service boundary** — this project never returns an entity from a
  service method that a controller serializes; even `reAssignAppointmentToAnotherDoctor` returns an
  entity only internally, and endpoints go through DTOs.
- **Use ModelMapper (Approach A) for straightforward entity→DTO flattening** where you already have
  (or need) the full entity — simple, DRY, no boilerplate.
- **Use a JPQL constructor expression (Approach B) for aggregates and narrow projections** where
  hydrating the full entity would be wasteful and the "DTO" is really a query result shape — as
  `countEachBloodGroupType` does. Only the needed columns cross the wire.
- **Keep request DTOs id-based** (`CreateAppointmentRequestDto` carries `doctorId`/`patientId`, not
  `Doctor`/`Patient`) so clients can't smuggle entity graphs or unexpected FKs into the persistence
  layer.
- **Keep a `@NoArgsConstructor` alongside `@AllArgsConstructor`** on query-projection DTOs (as
  `BloodGroupCountResponseEntity` does) so both the constructor expression and general JSON/deserialization
  paths work.

## 12. Performance Notes

- **Approach A costs a full entity hydration** — all mapped columns and any EAGER associations are
  loaded even if the DTO uses only a few fields. For `PatientResponseDto` that means `Patient`'s EAGER
  `appointments` are still fetched, then discarded during mapping.
- **Approach B costs only the selected columns/aggregates** — no entity, no EAGER-association side
  loads. For `countEachBloodGroupType`, only `(bloodGroup, count)` rows come back; far cheaper than
  loading every `Patient` and counting in Java.
- ModelMapper's reflection is negligible next to the DB round trip, but the *over-fetch* it can hide
  (loading associations you then drop) is the real cost — pick Approach B when the DTO is much
  narrower than the entity.

## 13. Interview Questions

- Q: Why not just return JPA entities from controllers?
  A: Leaks lazy proxies (`Appointment.doctor` → `LazyInitializationException`), leaks security fields
  (`User.password`/`roles` via the shared PK), over-serializes EAGER collections
  (`Patient.appointments`), and couples the wire contract to the schema. DTOs decouple all four.
- Q: What are the two DTO-building strategies in this project and when do you use each?
  A: (1) ModelMapper post-fetch — fetch the entity, `modelMapper.map(entity, Dto.class)`; simple,
  good for flattening a full entity. (2) JPQL constructor expression — `SELECT new Dto(...)`; the DTO
  is built in the query, no entity hydration, ideal for aggregates like `Count(p)`.
- Q: What breaks if you reorder `BloodGroupCountResponseEntity`'s constructor args?
  A: The JPQL `SELECT new ...(p.bloodGroup, Count(p))` in `countEachBloodGroupType` no longer matches
  the constructor — it fails at query execution, with no compile-time error, because the JPQL string
  isn't type-checked against the class.
- Q: Where is the `ModelMapper` defined and how is it wired in?
  A: A single `@Bean` in `config/AppConfig.java`, constructor-injected (via
  `@RequiredArgsConstructor`) into `PatientService`, `DoctorService`, `AppointmentService`.

## 14. Summary

DTOs separate the API contract from the persistence model, protecting the wire from lazy proxies
(`Appointment.doctor`), security fields (`User.password`/`roles` behind the `@MapsId` shared PK),
over-fetched EAGER collections (`Patient.appointments`), and schema churn. This project builds them two
ways: **ModelMapper** (`config/AppConfig.java`'s bean, called as `modelMapper.map(...)` across
`PatientService`/`DoctorService`/`AppointmentService`) hydrates the full entity then copies fields by
reflection; a **JPQL constructor expression** (`PatientRepository.countEachBloodGroupType` building
`BloodGroupCountResponseEntity`) builds the DTO inside the query, ideal for the `Count(p)` aggregate
that has no entity home. Use ModelMapper for flattening entities you already hold; use the constructor
expression for narrow/aggregate projections — at the cost of a query that isn't compile-time checked
against the DTO's constructor. `AppointmentResponseDto`'s commented-out `patient` field is the tidy
reminder that a DTO's shape is a deliberate contract, not a mirror of the entity.
