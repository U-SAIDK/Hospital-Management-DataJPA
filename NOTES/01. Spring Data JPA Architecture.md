# Spring Data JPA Architecture

## 1. Definition

Spring Data JPA is a Spring module that sits on top of a JPA provider (Hibernate, in this project) and
generates repository implementations at runtime from interfaces you declare. It is not a JPA
provider itself — it's a productivity layer that turns `interface FooRepository extends JpaRepository<Foo, Long>`
into a fully working, transactional data-access bean without you writing a single line of
implementation code.

## 2. Core Idea

There are four layers between your service code and the database, each with a distinct job:

```
Repository interface (yours)  →  Spring Data JPA proxy  →  JPA provider (Hibernate)  →  JDBC  →  DB
```

- **Repository interface** — declares *what* data you want (`findByName`, `save`, `existsById`).
- **Spring Data JPA proxy** — a runtime-generated implementation that turns interface method calls
  into `EntityManager` calls, and, for derived methods, builds a `CriteriaQuery`/JPQL string from
  the method name itself.
- **JPA provider (Hibernate)** — translates JPQL/Criteria into SQL, manages the persistence context
  (first-level cache, dirty checking), and handles entity lifecycle.
- **JDBC** — the actual wire protocol Hibernate uses to talk to PostgreSQL.

## 3. Why We Need It

Without Spring Data JPA, every repository would need a hand-written class implementing basic CRUD
(`save`, `findById`, `delete`, ...) plus an `EntityManager` injected and boilerplate query-building
code for every custom finder. Spring Data JPA eliminates that boilerplate: you write an interface,
Spring generates the implementation. It also wires the `EntityManagerFactory` and
`PlatformTransactionManager` for you via Spring Boot autoconfiguration, so a learning project like
this one can go from zero to a working persistence layer with almost no infrastructure code.

## 4. Internal Working

At startup, `JpaRepositoriesAutoConfiguration` (triggered because `spring-boot-starter-data-jpa` is
on the classpath) scans for interfaces extending `Repository`/`JpaRepository`. For each one it
registers a `JpaRepositoryFactoryBean`, which at bean-creation time:

1. Creates a JDK dynamic proxy implementing your repository interface.
2. Backs that proxy with a `SimpleJpaRepository` instance (the concrete class providing `save`,
   `findById`, `findAll`, `delete`, etc., all implemented against an injected `EntityManager`).
3. For any method that isn't inherited from `JpaRepository` (e.g. `findByName`), parses the method
   name into a query, or — if a `@Query` annotation is present — uses that JPQL/native SQL directly.
   This parsing happens once, at startup, not on every call.

Separately, `DataSourceAutoConfiguration` and `HibernateJpaAutoConfiguration` build the
`DataSource`, `LocalContainerEntityManagerFactoryBean`, and `JpaTransactionManager` beans purely
from `application.properties` — nothing in this project defines these beans by hand. Confirmed by
reading `pom.xml` (only `spring-boot-starter-data-jpa` + `org.postgresql:postgresql` dependencies,
no manual `DataSource`/`EntityManagerFactory` bean anywhere in `config/AppConfig.java`) and
`src/main/resources/application.properties`, which only sets `spring.datasource.url/username/password`,
`spring.jpa.hibernate.ddl-auto=create`, and `spring.jpa.show-sql=true` — plain properties, no
`@Bean`-defined infrastructure.

## 5. Flow Diagram (ASCII)

```
 HTTP request
     │
     ▼
 @RestController          controller/*.java  (thin, delegates only)
     │
     ▼
 @Service (+@Transactional) service/*.java    (business logic, DTO<->Entity via ModelMapper)
     │
     ▼
 Repository interface       repository/*.java  (e.g. PatientRepository extends JpaRepository<Patient, Long>)
     │   (call intercepted by dynamic proxy)
     ▼
 SimpleJpaRepository        Spring Data JPA's generated implementation
     │
     ▼
 EntityManager / Hibernate Session   (persistence context, dirty checking, SQL generation)
     │
     ▼
 JDBC driver (org.postgresql)
     │
     ▼
 PostgreSQL (hospitalDB)
```

## 6. Real-world Analogy

Think of a restaurant. You (the service layer) don't walk into the kitchen and cook — you hand a
ticket to a waiter (the repository interface) describing what you want (`findByName`). The waiter
doesn't cook either; they hand it to the kitchen (Hibernate), which translates the order into
actual cooking steps (SQL) and talks to the pantry/suppliers (JDBC/DB). Spring Data JPA is the
waiter: it's generated for you, standardized, and you never have to train a new one for a new menu
item (repository) — you just write the ticket format (method signature).

## 7. How THIS PROJECT Uses It

Every repository in this project (`repository/PatientRepository.java`, `DoctorRepository.java`,
`AppointmentRepository.java`, `DepartmentRepository.java`, `InsuranceRepository.java`,
`UserRepository.java`) is a plain interface extending `JpaRepository<Entity, Long>` — none of them
have a hand-written implementation class anywhere in `src/main/java`. The layered architecture is:

```
controller/*.java  →  service/*.java (@Service, @Transactional)  →  repository/*.java (interfaces)  →  entity/*.java
```

Concretely: `AdminController` → `DoctorService`/`PatientService` → `DoctorRepository`/`PatientRepository`
→ `Doctor`/`Patient` entities. `PatientController` → `AppointmentService`/`PatientService` →
`AppointmentRepository`/`PatientRepository`/`DoctorRepository` → `Appointment`/`Patient`/`Doctor`.
No controller talks to a repository directly, and no repository has business logic — that
separation is consistent across the whole codebase.

## 8. Code Example From This Project

```java
// repository/DoctorRepository.java
public interface DoctorRepository extends JpaRepository<Doctor, Long> {
}
```

```java
// service/DoctorService.java
@Transactional
public DoctorResponseDto onBoardNewDoctor(OnboardDoctorRequestDto onBoardDoctorRequestDto) {
    User user = userRepository.findById(onBoardDoctorRequestDto.getUserId()).orElseThrow();
    if(doctorRepository.existsById(onBoardDoctorRequestDto.getUserId())) {
        throw new IllegalArgumentException("Already a doctor");
    }
    ...
    return modelMapper.map(doctorRepository.save(doctor), DoctorResponseDto.class);
}
```

## 9. Line-by-Line Explanation

- `DoctorRepository extends JpaRepository<Doctor, Long>` — no method bodies, no implementation
  class; this single line is enough for `existsById`, `findById`, and `save` (used below) to work
  at runtime because `JpaRepositoryFactoryBean` builds the proxy for you.
- `userRepository.findById(...)` and `doctorRepository.existsById(...)` — both calls resolve to
  `SimpleJpaRepository` methods backed by the same injected `EntityManager` Spring Boot
  autoconfigured from `application.properties`'s `spring.datasource.*` properties — no manual
  `EntityManager` wiring exists in this project.
- `doctorRepository.save(doctor)` — Spring Data JPA inspects whether the entity's `@Id` is null
  (new/transient) or set (existing/detached) to decide between `EntityManager.persist()` (INSERT)
  and `merge()` (UPDATE); here `doctor` is freshly built via `Doctor.builder()`, so it's an INSERT.

## 10. Common Mistakes

- Assuming a repository interface needs an `@Repository`-annotated implementation class somewhere —
  it doesn't; Spring Data generates it entirely.
- Believing derived-method parsing happens on every call (a performance worry) — it's parsed once
  at application startup, not per invocation.
- Forgetting that `spring.jpa.hibernate.ddl-auto=create` (used in this project, see
  `application.properties`) drops and recreates the schema on every restart — fine for this
  learning project, but would destroy production data if left set that way.

## 11. Best Practices

- Keep repository interfaces free of business logic — this project's repositories are pure data
  access, all business rules (e.g. `onBoardNewDoctor`'s "already a doctor" check) live in the
  `@Service` layer.
- Prefer the narrowest repository interface that gives you what you need — most repositories here
  extend `JpaRepository` even though several (e.g. `DoctorRepository`) don't yet use anything beyond
  basic CRUD, keeping the door open for query methods later without extra ceremony.
- In real (non-learning) projects, switch `ddl-auto` to `validate` or use a migration tool
  (Flyway/Liquibase) instead of `create`.

## 12. Performance Notes

- Derived query parsing cost is paid once at startup (bean creation), not per request — so even a
  method name like `findByNameContainingOrderByIdDesc` (`PatientRepository`) has zero extra
  reflection overhead at call time.
- The proxy indirection (interface → dynamic proxy → `SimpleJpaRepository`) adds negligible
  overhead per call compared to the actual JDBC round trip; the real cost driver is always the
  generated SQL and network/DB time, not the Spring Data layer itself.

## 13. Interview Questions

- Q: How does Spring Data JPA implement a repository interface with no code in it?
  A: Via `JpaRepositoryFactoryBean`, which creates a JDK dynamic proxy delegating to a
  `SimpleJpaRepository` (or a parsed-query invocation) backed by an `EntityManager`.
- Q: What beans does `spring-boot-starter-data-jpa` autoconfigure, and where are they defined in
  this project?
  A: `DataSource`, `LocalContainerEntityManagerFactoryBean`, `JpaTransactionManager` — none are
  defined by hand anywhere in this codebase; they come purely from `application.properties` values.
- Q: Where does business logic belong relative to the repository layer?
  A: In the `@Service` layer (e.g. `DoctorService`, `AppointmentService`) — repositories in this
  project contain zero business rules.

## 14. Summary

Spring Data JPA is the glue between plain repository interfaces and Hibernate: it generates the
implementation via dynamic proxies, autoconfigures the JPA infrastructure (`DataSource`,
`EntityManagerFactory`, transaction manager) purely from properties, and lets this project's
architecture stay a clean `controller → service → repository → entity` chain with zero
hand-written data-access boilerplate anywhere in `repository/*.java`.
