# Entity Relationships

## 1. Definition

Entity relationships are the JPA mappings (`@OneToOne`, `@OneToMany`, `@ManyToOne`, `@ManyToMany`)
that model how rows in different tables reference each other. Each association has an **owning side**
(the entity whose mapping controls the actual foreign key / join-table writes) and, if bidirectional,
an **inverse side** (declared with `mappedBy`, read-only from the DB-write perspective).

## 2. Core Idea

Only the owning side matters to the database. The owning side is the one that physically holds the FK
column (`@JoinColumn`) or defines the join table (`@JoinTable`). The inverse side (`mappedBy = "…"`)
is purely a navigation convenience — changing its collection in memory does NOT by itself produce any
SQL. Getting owning-vs-inverse right is the difference between a change persisting and silently
vanishing.

## 3. Why We Need It

A hospital domain is a graph: a `User` is either a `Patient` or a `Doctor`; a `Patient` has one
`Insurance` and many `Appointments`; a `Doctor` belongs to many `Department`s and has many
`Appointment`s. Modelling these as typed associations lets code navigate the object graph
(`patient.getAppointments()`), lets Hibernate cascade lifecycle operations (delete a `Patient` →
delete their `Insurance` and `Appointment`s), and keeps referential integrity enforced by real FK
constraints rather than application code.

## 4. Internal Working

- **Owning `@ManyToOne` / `@OneToOne` with `@JoinColumn`** — the entity's table gets an FK column;
  setting the field and flushing writes that FK.
- **`mappedBy` (inverse side)** — no FK column here; Hibernate reads the association by querying the
  owning side's FK. Mutating this collection alone changes nothing in the DB.
- **`@ManyToMany` + `@JoinTable`** — the owning side defines a separate join table with `joinColumns`
  (FK back to itself) and `inverseJoinColumns` (FK to the other side); inserts/deletes on the owning
  collection write join-table rows.
- **`@OneToOne @MapsId`** — shared primary key: the dependent entity's `@Id` is *the same value* as
  the referenced entity's id, so there is no separate id sequence; the PK doubles as the FK.
- **Fetch defaults** — `@ManyToOne`/`@OneToOne` default to EAGER; `@OneToMany`/`@ManyToMany` default
  to LAZY. Individual mappings override these.
- **Cascade / orphanRemoval** — cascade propagates persist/remove from owner to associated entity;
  `orphanRemoval=true` deletes the child when it's removed from the owner (including nulling a
  `@OneToOne` reference).

## 6. Real-world Analogy

Think of a filing office. The **owning side** is whoever physically keeps the cross-reference slip in
their folder — that slip is the FK, and only they can change the filed relationship. The **inverse
side** is someone who keeps a *photocopy* for convenience: handy to read, but editing the photocopy
never changes the official file. `@MapsId` is like giving a patient's medical file the *same case
number* as their citizen ID instead of issuing a new number — one identifier serves both.

## 7. How THIS PROJECT Uses It

Precise owning-vs-inverse breakdown, verified against the entity files:

- **`User` ↔ `Doctor`** and **`User` ↔ `Patient`** — shared PK. `Doctor.user` and `Patient.user` are
  `@OneToOne @MapsId`; the dependent's id IS the User's id. A `User` is *either* a Patient or a Doctor,
  keyed off the same id (no separate sequence).
- **`Doctor` ↔ `Department`** (`@ManyToMany`) — **`Department` owns** it via
  `@JoinTable(name="my_dpt_doctors", joinColumns=@JoinColumn(name="dpt_id"),
  inverseJoinColumns=@JoinColumn(name="doctor_id"))`. **`Doctor` is inverse**:
  `@ManyToMany(mappedBy="doctors")`. Only changes to `Department.doctors` write the join table.
- **`Patient` ↔ `Insurance`** (`@OneToOne`) — **`Patient` owns** it:
  `@OneToOne(cascade=ALL, orphanRemoval=true) @JoinColumn(name="patient_insurance_id")`.
  **`Insurance` is inverse**: `@OneToOne(mappedBy="insurance")`. The FK lives on `patient`.
- **`Patient`/`Doctor` ↔ `Appointment`** (`@ManyToOne`) — **`Appointment` owns** both FKs:
  `@ManyToOne @JoinColumn(name="patient_id", nullable=false)` (default EAGER) and
  `@ManyToOne(fetch=LAZY) @JoinColumn(nullable=false)` for `doctor`. `Patient.appointments`
  (`mappedBy="patient"`, EAGER) and `Doctor.appointments` (`mappedBy="doctor"`, LAZY) are inverse.
  Both FK fields on `Appointment` are `@ToString.Exclude`d to avoid recursive/lazy-init toString bugs.
- **`Department` → `Doctor`** (`headDoctor`) — unidirectional `@OneToOne` (no `mappedBy` on Doctor);
  Department holds the FK and Doctor has no way back to "the department I head."

Behavioural cross-references (in the service layer):

- **Dirty checking** — `AppointmentService.reAssignAppointmentToAnotherDoctor` sets
  `appointment.setDoctor(doctor)` on a managed entity inside `@Transactional` and returns with NO
  `save()`; Hibernate detects the change at flush and issues the UPDATE.
- **In-memory bidirectional consistency** — both `createNewAppointment`
  (`patient.getAppointments().add(appointment)`) and `reAssignAppointmentToAnotherDoctor`
  (`doctor.getAppointments().add(appointment)`) update the *inverse* collection purely for object-graph
  correctness; it does not affect what's persisted (only the owning FK does).
- **orphanRemoval delete** — `InsuranceService.disaccociateInsuranceFromPatient` calls
  `patient.setInsurance(null)`; because `Patient.insurance` has `orphanRemoval=true`, Hibernate DELETEs
  the Insurance row on flush rather than just nulling an FK.

## 8. Code Example From This Project

```java
// entity/Patient.java  — Patient OWNS the Insurance relationship (holds the FK)
@OneToOne(cascade = {CascadeType.ALL}, orphanRemoval = true)
@JoinColumn(name = "patient_insurance_id") // owning side
private Insurance insurance;

@OneToMany(mappedBy = "patient", cascade = {CascadeType.REMOVE}, orphanRemoval = true, fetch = FetchType.EAGER)
private List<Appointment> appointments = new ArrayList<>();

@OneToOne
@MapsId                                    // Patient's PK IS the User's PK
private User user;
```

```java
// entity/Insurance.java  — INVERSE side, no FK column here
@OneToOne(mappedBy = "insurance") // inverse side
private Patient patient;
```

```java
// entity/Department.java  — Department OWNS the M:N join table
@ManyToMany
@JoinTable(
        name = "my_dpt_doctors",
        joinColumns = @JoinColumn(name = "dpt_id"),
        inverseJoinColumns = @JoinColumn(name = "doctor_id")
)
private Set<Doctor> doctors = new HashSet<>();
```

```java
// entity/Doctor.java  — INVERSE side of the M:N
@ManyToMany(mappedBy = "doctors")
private Set<Department> departments = new HashSet<>();
```

```java
// entity/Appointment.java  — Appointment OWNS both FKs (patient_id, doctor)
@ManyToOne
@ToString.Exclude
@JoinColumn(name = "patient_id", nullable = false)   // EAGER by default
private Patient patient;

@ManyToOne(fetch = FetchType.LAZY)
@ToString.Exclude
@JoinColumn(nullable = false)
private Doctor doctor;
```

## 9. Line-by-Line Explanation

- `@OneToOne @MapsId private User user;` (in `Patient` and `Doctor`) — `@MapsId` makes the entity's
  `@Id` copy the `User`'s id, so `patient_id == user_id`. There is no independent Patient/Doctor id
  sequence, and a Patient/Doctor row can only exist for an existing User.
- `@OneToOne(cascade=ALL, orphanRemoval=true) @JoinColumn(name="patient_insurance_id")` — `Patient` is
  the **owner**: this table gets the `patient_insurance_id` FK. `cascade=ALL` means saving/deleting a
  Patient saves/deletes its Insurance; `orphanRemoval=true` means removing the reference (setting it
  null) deletes the Insurance row — exactly what `disaccociateInsuranceFromPatient` relies on.
- `@OneToOne(mappedBy = "insurance") private Patient patient;` (in `Insurance`) — the **inverse**
  side. No FK column; `mappedBy` points at the owning `Patient.insurance` field. Setting
  `insurance.setPatient(...)` alone (as `assignInsuranceToPatient` does for consistency) writes
  nothing — the owning `patient.setInsurance(...)` is what persists.
- `@JoinTable(name="my_dpt_doctors", joinColumns=@JoinColumn(name="dpt_id"),
  inverseJoinColumns=@JoinColumn(name="doctor_id"))` — `Department` **owns** the M:N; the join table
  has `dpt_id` (FK to Department) and `doctor_id` (FK to Doctor). Only mutating `Department.doctors`
  writes rows here.
- `@ManyToMany(mappedBy = "doctors")` (in `Doctor`) — **inverse**; `Doctor.departments` is a
  read-through view of the same join table, driven by Department's side.
- `@ManyToOne @JoinColumn(name="patient_id", nullable=false)` (in `Appointment`) — owning FK to
  Patient; `@ManyToOne` defaults to **EAGER**, so loading an Appointment loads its Patient. `nullable=false`
  makes patient mandatory.
- `@ManyToOne(fetch=LAZY) @JoinColumn(nullable=false)` for `doctor` — owning FK to Doctor, explicitly
  **LAZY**, so the doctor is a proxy until accessed — a deliberate contrast with the EAGER patient.
- `@ToString.Exclude` on both — keeps Lombok's `toString` from recursing into `Patient` (and its EAGER
  appointments) or forcing the lazy `Doctor` proxy to initialise just to print.
- `@OneToMany(mappedBy="patient", cascade=REMOVE, orphanRemoval=true, fetch=EAGER)` — inverse
  collection on Patient; EAGER here vs LAZY on `Doctor.appointments` is an intentional teaching
  contrast. `cascade=REMOVE`+`orphanRemoval` mean deleting a Patient deletes their Appointments.

## 10. Common Mistakes

- **Updating only the inverse side and expecting it to persist.** Adding to `Doctor.appointments`
  (inverse) writes nothing; only setting `Appointment.doctor` (owner) does. The services set the
  owning side first and update the inverse collection *only* for in-memory consistency.
- **Confusing which side owns the M:N.** Here `Department` owns `my_dpt_doctors`; trying to manage the
  membership via `Doctor.departments` (inverse) would silently no-op.
- **Forgetting `@ToString.Exclude` on bidirectional/lazy associations.** Without it, `toString` on
  `Appointment` recurses through `Patient`↔`Appointment` or triggers `LazyInitializationException` on
  the doctor proxy.
- **Expecting a separate id for a `@MapsId` entity.** `Doctor`/`Patient` don't get their own id
  sequence — their id is the `User`'s id; treating them as independently keyed leads to confusion when
  saving.
- **Assuming nulling a `@OneToOne` just clears the FK.** With `orphanRemoval=true` it DELETEs the
  child row (`disaccociateInsuranceFromPatient`), which surprises people expecting a soft detach.

## 11. Best Practices

- Always mutate the **owning** side to change what's persisted; update the inverse side too only for
  object-graph consistency, as this project does explicitly (`// to maintain consistency`).
- Make to-one associations LAZY when the related fields aren't always needed (`Appointment.doctor`) to
  avoid unnecessary joins; the project keeps this as a conscious EAGER/LAZY contrast.
- Use `@MapsId` for genuine one-to-one identity sharing (a User that *is* a Doctor/Patient) instead of
  inventing a redundant FK plus separate PK.
- Scope cascade + orphanRemoval to true parent/child ownership (`Patient`→`Insurance`,
  `Patient`→`Appointment`) where the child cannot meaningfully exist without the parent.
- Exclude bidirectional/lazy associations from Lombok `toString`/`equals`/`hashCode` to prevent
  recursion and accidental lazy loading.

## 12. Performance Notes

- **`Appointment.patient` is EAGER** (default `@ManyToOne`), so every Appointment load joins/fetches
  its Patient even when unneeded; **`Appointment.doctor` is LAZY**, deferring the doctor query until
  accessed — the LAZY choice avoids a join on the common read path.
- **`Patient.appointments` is EAGER** — loading any Patient also loads all their appointments; on a
  patient with many appointments this is a heavier load than Doctor's LAZY collection, and can
  contribute to N+1 across a list of patients (mitigated by `findAllPatientWithAppointment`'s
  `JOIN FETCH`).
- **`@MapsId` shared PK** means the `@OneToOne` to `User` needs no extra FK column and joins on the
  primary key — the cheapest possible join.
- **Cascade + orphanRemoval** turns a single `patient.setInsurance(null)` or Patient delete into
  additional DELETE statements at flush; correct, but worth knowing it multiplies the SQL issued.

## 13. Interview Questions

- Q: What is the difference between the owning and inverse side?
  A: The owning side holds the FK/join table and controls DB writes; the inverse side uses `mappedBy`
  and is navigation-only — changing it alone persists nothing. Example: `Patient` owns `Insurance`;
  `Insurance.patient` is inverse.
- Q: What does `@MapsId` do here?
  A: It makes `Doctor`/`Patient` share the `User`'s primary key — their id equals the User's id, so no
  separate id sequence exists and the PK doubles as the FK to `User`.
- Q: Why is `Appointment.doctor` LAZY but `patient` EAGER?
  A: `@ManyToOne` defaults to EAGER (patient), while `doctor` explicitly opts into LAZY so it's fetched
  as a proxy only when accessed — a deliberate contrast and a load-path optimisation.
- Q: How does the project delete an Insurance without a repository delete call?
  A: `Patient.insurance` has `orphanRemoval=true`, so `patient.setInsurance(null)` in
  `disaccociateInsuranceFromPatient` makes Hibernate DELETE the orphaned Insurance at flush.
- Q: Which side manages the `Doctor`/`Department` membership?
  A: `Department` — it owns the `my_dpt_doctors` join table via `@JoinTable`; `Doctor.departments` is
  the inverse (`mappedBy="doctors"`).

## 14. Summary

This project's object graph hangs off `User`: `Doctor` and `Patient` share `User`'s primary key via
`@OneToOne @MapsId`. `Department` owns the `Doctor`↔`Department` many-to-many (`@JoinTable
my_dpt_doctors`), with `Doctor.departments` inverse. `Patient` owns its `Insurance`
(`@JoinColumn patient_insurance_id`, cascade=ALL, orphanRemoval) with `Insurance.patient` inverse.
`Appointment` owns both FK sides to `Patient` (EAGER) and `Doctor` (LAZY). The owning side always
drives persistence — which is exactly why `AppointmentService` sets the owning FK for real writes and
touches inverse collections only for in-memory consistency, why dirty checking updates a reassigned
doctor with no `save()`, and why nulling `Patient.insurance` deletes the Insurance via orphanRemoval.
