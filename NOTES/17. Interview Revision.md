# Interview Revision — Q&A

A topic-organized revision set. Every answer is grounded in this project's real code where it helps.
Concept deep-dives live in the numbered `NOTES/` files and `src/MASTER_NOTES.md`; this file is the
rapid-recall layer. Paths are under
`src/main/java/com/codingshuttle/youtube/hospitalManagement/` unless noted.

## Entities & Mapping

**Q1. What does a class need to be a JPA entity here?**
`@Entity` plus an `@Id`. Every entity in `entity/*.java` also carries Lombok
`@Getter/@Setter/@NoArgsConstructor` — the no-arg constructor is required because Hibernate
instantiates entities reflectively before populating fields. `@Builder`/`@AllArgsConstructor` are for
*your* convenience (e.g. `Appointment.builder()`), not Hibernate's.

**Q2. `@GeneratedValue(strategy = IDENTITY)` vs `SEQUENCE` — which does this project use and why does it
matter?**
All standalone entities use `GenerationType.IDENTITY` (`Patient`, `Doctor`, `Appointment`, `User`,
`Department`, `Insurance`). IDENTITY delegates id generation to the DB's auto-increment column, so the
id isn't known until the INSERT executes (Hibernate can't batch such inserts as aggressively as
SEQUENCE). SEQUENCE pre-fetches ids from a DB sequence and allows batching — not used here.

**Q3. What is `@MapsId` and where is it used?**
`@MapsId` makes an entity's primary key be *the same value as* an associated entity's PK (shared
primary key). `Doctor.user` and `Patient.user` both use `@OneToOne @MapsId User user` — so a `Doctor`
/`Patient` row's id **is** its `User`'s id, with no separate `doctor_id`/`patient_id` sequence. A
`Doctor`/`Patient` can only exist for an existing `User`. This is why `onBoardNewDoctor` can call
`doctorRepository.existsById(userId)` — the doctor's id *is* the user's id.

**Q4. `@Enumerated(EnumType.STRING)` vs `ORDINAL` — why STRING everywhere?**
`Patient.bloodGroup`, `User.providerType`, and `User.roles` all use `EnumType.STRING`. STRING stores
the enum *name* (`"A_POSITIVE"`), so reordering or inserting enum constants never corrupts existing
rows. ORDINAL stores the position (0,1,2...), which silently breaks if the enum order changes — a
classic data-corruption trap this project deliberately avoids.

**Q5. What is `@ElementCollection` and why does `User.roles` use it (with `fetch = EAGER`)?**
`User.roles` is `@ElementCollection @Enumerated(STRING) Set<RoleType>` — a collection of *value types*
(plain enums), stored in a separate collection table, **not** a related entity. It's `EAGER` because
`getAuthorities()` reads roles during authentication, which can run outside the original persistence
context; a LAZY collection would throw `LazyInitializationException` there.

**Q6. Owning vs inverse side — give a concrete example.**
For the `Department`↔`Doctor` many-to-many: `Department.doctors` is the **owning** side (it declares
`@JoinTable(name="my_dpt_doctors", ...)`, so its collection changes are what get written), and
`Doctor.departments` is the **inverse** side (`@ManyToMany(mappedBy = "doctors")`, effectively
read-only for persistence). Only the owning side controls the join table.

**Q7. What unique constraints does `Patient` enforce, and what's odd about them?**
`Patient` has a composite `@UniqueConstraint` on `(name, birthDate)`
(`unique_patient_name_birthdate`). A `@UniqueConstraint` on `email` was tried and **commented out** —
but `@Column(unique = true)` on `email` still enforces email uniqueness, so the commented line is
currently redundant. A good example of an evolving-schema decision left visible in the code.

## Repositories & Queries

**Q8. `JpaRepository` vs `CrudRepository` — what's the difference and which does this project use?**
`CrudRepository` gives basic CRUD. `PagingAndSortingRepository` adds `Pageable`/`Sort`. `JpaRepository`
extends both and adds JPA-specific extras — batch operations, `flush()`/`saveAndFlush()`,
`getReferenceById`, and `List`-returning overloads. Every repository here extends
`JpaRepository<Entity, Long>` (`repository/*.java`) — which is why `PatientRepository.findAllPatients`
can return `Page<Patient>` and take a `Pageable` out of the box.

**Q9. Derived query methods vs `@Query` (JPQL) vs native SQL — show all three from one repository.**
`PatientRepository` has all three:
- Derived: `findByName`, `findByBirthDateOrEmail`, `findByBirthDateBetween`,
  `findByNameContainingOrderByIdDesc` — Spring Data parses the method name into a query at startup.
- JPQL `@Query`: `findByBloodGroup`, `findByBornAfterDate` — written against entity/field names.
- Native `@Query(nativeQuery = true)`: `findAllPatients` — raw SQL against the `patient` table.
Derived methods are parsed **once at startup**, not per call.

**Q10. What does `@Modifying` do, and why does `updateNameWithId` also need `@Transactional`?**
`@Modifying` tells Spring Data the `@Query` is a DML statement (UPDATE/DELETE), not a SELECT — without
it Spring Data tries to run it as a query and fails. `PatientRepository.updateNameWithId` also carries
`@Transactional` because a bulk update must run inside a transaction. Caveat: it's a **bulk** UPDATE
that bypasses the persistence context — if a `Patient` with that id is already managed, it goes stale
until refreshed (contrast the dirty-checking path in `AppointmentService`).

**Q11. What is a JPQL constructor-expression projection?**
`SELECT new <FQCN>(...)` builds a DTO directly from the query result rather than loading entities.
`PatientRepository.countEachBloodGroupType` does
`select new com.codingshuttle...BloodGroupCountResponseEntity(p.bloodGroup, Count(p)) ... group by
p.bloodGroup`. The DTO's `@AllArgsConstructor` parameter order/types must exactly match the `SELECT
new(...)` list — a rename breaks the JPQL silently (no compile-time check). See `NOTES/15`.

**Q12. Where is the repository implementation code?**
Nowhere hand-written. Spring Data generates a JDK dynamic proxy backed by `SimpleJpaRepository` at
startup for each interface — `repository/*.java` are pure interfaces. See `NOTES/01`.

## Persistence Context & Lifecycle

**Q13. What are the four entity states? Ground each in this code.**
- **Transient** — `Appointment.builder()...build()` in `AppointmentService.createNewAppointment`
  before `save()`; not known to Hibernate.
- **Managed** — the result of `findById(...)`/`save(...)` inside an active persistence context; changes
  are tracked (e.g. the `appointment` in `reAssignAppointmentToAnotherDoctor`).
- **Detached** — a once-managed entity after its transaction/session closed (e.g. an entity returned
  from a `@Transactional` service to a non-transactional caller); further changes aren't tracked.
- **Removed** — scheduled for deletion, e.g. the `Insurance` orphaned by
  `InsuranceService.disaccociateInsuranceFromPatient`.

**Q14. What is the persistence context and how many are there per request here?**
It's Hibernate's `Session` — the first-level cache and change-tracking table. One per transaction here
(no open-session-in-view override), scoped to a `@Transactional` method. It's what makes dirty
checking and `@MapsId` shared-key resolution work without extra queries. See `MASTER_NOTES.md` §6.

**Q15. What is `LazyInitializationException` and where could it fire in this project?**
It fires when you access a LAZY association *after* its persistence context has closed. Candidate:
`Appointment.doctor` (`@ManyToOne(fetch = LAZY)`) — accessing `.getDoctor()`'s fields on a detached
`Appointment` (outside the transaction) would throw it. This is a core reason the code maps entities to
DTOs *inside* the transactional service methods before returning.

**Q16. Why does `save()` sometimes INSERT and sometimes UPDATE?**
`SimpleJpaRepository.save` checks whether the entity is "new" (typically a null `@Id`). New → `persist`
(INSERT); existing/detached → `merge` (UPDATE). In `DoctorService.onBoardNewDoctor`, `doctor` is
freshly built via `Doctor.builder()`, so `save` INSERTs.

## Transactions

**Q17. What does `@Transactional`'s default `propagation = REQUIRED` mean?**
REQUIRED (the default) means: join the caller's existing transaction if one is active, otherwise start
a new one. So when `AppointmentService.createNewAppointment` (itself `@Transactional`) runs, all its
repository calls execute within that single transaction — atomic, one commit at the end.

**Q18. `jakarta.transaction.Transactional` vs
`org.springframework.transaction.annotation.Transactional` — which does this project use?**
Consistently the **JTA** one, `jakarta.transaction.Transactional` (verify the imports in
`AppointmentService`, `PatientService`, `DoctorService`, `InsuranceService`, `AuthService`,
`PatientRepository`). Spring honors it fine, though it exposes fewer knobs than Spring's own annotation
(e.g. no `readOnly`, different rollback-rule defaults). For this learning project the JTA annotation is
sufficient.

**Q19. Why does `AppointmentService.reAssignAppointmentToAnotherDoctor` not call `save()`?**
Because `appointment` was loaded via `findById` inside a `@Transactional` method, it's *managed*.
Calling `appointment.setDoctor(doctor)` mutates a managed entity; Hibernate's **dirty checking**
compares it to the load-time snapshot at commit and issues the UPDATE automatically. `save()` would be
redundant. This is the canonical dirty-checking example (`MASTER_NOTES.md` §5).

**Q20. Why does the bulk `updateNameWithId` need its own transaction while dirty checking "just works"
elsewhere?**
Dirty-checking updates ride along inside whatever service transaction is already open. A `@Modifying`
bulk UPDATE in the repository has no surrounding service transaction of its own, so it declares
`@Transactional` directly. It also *bypasses* the persistence context — no dirty checking, no entity
listeners.

**Q21. Why is `onBoardNewDoctor` `@Transactional` specifically?**
It performs two mutations that must be atomic: creating a `Doctor` row **and** adding `RoleType.DOCTOR`
to the linked `User`. A user elevated to DOCTOR without a `Doctor` row (or vice versa) would be
inconsistent — the transaction guarantees both or neither.

## Relationships & Fetching

**Q22. What are the default `FetchType`s per relationship, and where does this project follow vs
override them?**
Defaults: `@OneToOne` = EAGER, `@ManyToOne` = EAGER, `@OneToMany` = LAZY, `@ManyToMany` = LAZY. In this
code:
- `Appointment.patient` — `@ManyToOne` with no override → **EAGER** (the default).
- `Appointment.doctor` — `@ManyToOne(fetch = LAZY)` → **overrides** the default to LAZY.
- `Patient.appointments` — `@OneToMany(... fetch = EAGER)` → **overrides** the LAZY default to EAGER.
- `Doctor.appointments` — `@OneToMany(mappedBy = "doctor")` → **LAZY** (the default, left as-is).
The `Patient` (EAGER) vs `Doctor` (LAZY) appointments pair is a deliberate teaching contrast.

**Q23. What cascade types does this project actually use?**
Only two: `CascadeType.ALL` on `Patient.insurance` (Patient fully owns Insurance's lifecycle) and
`CascadeType.REMOVE` on `Patient.appointments` (deleting a Patient deletes its Appointments). The
others (PERSIST/MERGE/REFRESH/DETACH individually) are not used — don't claim otherwise.

**Q24. What is `orphanRemoval` and where does it bite?**
`orphanRemoval = true` deletes a child row when it's removed from the parent's reference, not just when
the parent is deleted. `Patient.insurance` has it, so
`InsuranceService.disaccociateInsuranceFromPatient` setting `patient.setInsurance(null)` **DELETEs** the
`Insurance` row on flush — not merely nulling a FK. See `MASTER_NOTES.md` §5.

**Q25. Why maintain both sides of a bidirectional association if only one is persisted?**
Only the FK-owning side (`Appointment.patient`/`.doctor`) affects the DB. Code like
`patient.getAppointments().add(appointment)` in `createNewAppointment` keeps the *in-memory* object
graph consistent so re-reading the collection in the same persistence context is correct — it has no
DB effect on its own.

## Performance

**Q26. What is the N+1 problem and does this project have one today?**
N+1 = 1 query for N parents + 1 query per parent for an association. Yes — `Patient.appointments` is
`EAGER`, so `patientRepository.findAll()` fires a per-patient appointment select. EAGER doesn't fix
N+1; it only makes the extra queries fire immediately. Fix: `findAllPatientWithAppointment`'s
`LEFT JOIN FETCH`. See `NOTES/14`.

**Q27. What's the cost of returning `Page<T>` vs `List<T>`?**
`Page<T>` runs a **second COUNT query** to compute `getTotalElements()`/`getTotalPages()`; `List`/`Slice`
don't. `PatientRepository.findAllPatients` returns `Page`, but `PatientService.getAllPatients` discards
the metadata into a `List` — paying for the COUNT and throwing it away. See `NOTES/13`.

**Q28. How would you debug generated SQL / spot N+1 in this project?**
`spring.jpa.show-sql=true` is already set in `application.properties` — run the method and count the
SELECTs in the console. `findAll()` on patients shows 1 + N; `findAllPatientWithAppointment` shows 1.

## Synthesis / Curveballs

**Q29. Why does `User` implementing `UserDetails` directly work here — and what's the tradeoff?**
`entity/User.java implements UserDetails`, so the JPA entity *is* the Spring Security principal — no
adapter/mapping layer. `CustomUserDetailsService.loadUserByUsername` returns the `User` entity as-is,
`JwtAuthFilter` puts it straight into the `SecurityContext`, and `AuthService.login` casts
`getPrincipal()` to `(User)` with no translation. `getAuthorities()` computes authorities on the fly
from `roles` via `RolePermissionMapping`. Tradeoff: it couples the persistence model to the security
framework — the entity now depends on `spring-security` types and must eagerly load `roles`
(`@ElementCollection(fetch = EAGER)`) so `getAuthorities()` works outside a session.

**Q30. Why is a second COUNT query needed for `Page` but not a plain `List`?**
`Page` promises `getTotalElements()`/`getTotalPages()` — that total can only be known by counting *all*
matching rows, which the page's `LIMIT`ed SELECT can't tell you. So Spring Data runs a separate
`SELECT COUNT(*)`. A `List`/`Slice` makes no such promise, so no count runs. See `NOTES/13`.

**Q31. What breaks if `BloodGroupCountResponseEntity`'s constructor arg order stops matching the JPQL?**
`countEachBloodGroupType`'s `SELECT new ...(p.bloodGroup, Count(p))` is matched to the constructor by
position/type at **runtime**, not compile time. Reordering/renaming/retyping the fields breaks the
query with a runtime error and no compiler warning. See `NOTES/15`.

**Q32. Every self-service signup becomes a Patient — how, and what about `SignUpRequestDto.roles`?**
`AuthService.signUpInternal` always creates a `User` *and* a `Patient` together (both plain and OAuth2
signup route through it). `SignUpRequestDto` carries a `roles` field, but the flow makes the account a
Patient regardless; Doctors are only created via `AdminController.onBoardNewDoctor`. The `roles` field
is a real gap worth noticing, not "fixing." See `NOTES/16` Flow 1.

**Q33. `@Secured` vs `@PreAuthorize` — why does `AppointmentService` use both?**
`@Secured("ROLE_PATIENT")` on `createNewAppointment` is a coarse role-only check (no SpEL, no method
args). `@PreAuthorize("hasAuthority('appointment:write') or #doctorId == authentication.principal.id")`
on `reAssignAppointmentToAnotherDoctor` uses SpEL to reach the *method argument* and the authenticated
principal — enabling a self-ownership check ("a doctor may only reassign their own appointments") that
a role check alone can't express. Both are enabled by `@EnableMethodSecurity`.

**Q34. Where is the `AuthenticationManager` defined and why expose it as a bean?**
`config/AppConfig.java` exposes Spring Security's internally-built `AuthenticationManager`
(`configuration.getAuthenticationManager()`) as a `@Bean` so `AuthService.login` can call
`authenticate(...)` directly instead of wiring a `DaoAuthenticationProvider` by hand. Under the hood it
still uses `CustomUserDetailsService` + the BCrypt `PasswordEncoder`.

**Q35. `ddl-auto=create` — what does it do and why is it wrong for production?**
`spring.jpa.hibernate.ddl-auto=create` (in `application.properties`) drops and recreates the entire
schema from the `@Entity` annotations on every startup — convenient for a learning project (schema
always matches the entities), catastrophic in production (it destroys all data). Real projects use
`validate` plus a migration tool (Flyway/Liquibase).
