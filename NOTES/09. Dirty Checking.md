# Dirty Checking

## 1. Definition

**Dirty checking** is Hibernate's mechanism for automatically detecting that a *managed* entity has
been modified since it was loaded, and emitting the corresponding UPDATE at flush time — without any
explicit `save()`/`update()` call. An entity is "dirty" when at least one of its persistent fields
differs from the snapshot Hibernate captured when the entity entered the persistence context.

## 2. Core Idea

Inside a transaction, you change an object; Hibernate figures out the SQL. When the persistence
context flushes (normally at commit), Hibernate walks every managed entity, compares its current
field values against the snapshot taken at load, and for each changed entity generates an UPDATE
that sets only what actually changed. Your code reads like plain object manipulation
(`appointment.setDoctor(doctor)`); the persistence layer turns that into the write.

## 3. Why We Need It

Dirty checking is what makes JPA feel like "objects that happen to be persistent" rather than a SQL
string builder:

- **No boilerplate UPDATEs** — you never write `UPDATE appointment SET doctor_id = ...`; you set a
  field.
- **Consistency** — every change made to managed entities in a unit of work is flushed together, in
  a FK-safe order, atomically with the transaction.
- **Minimal writes** — Hibernate can UPDATE only the changed columns, not the whole row.

It is the single feature behind this project's cleanest mutation method, and understanding what
*breaks* it explains several of the codebase's other design choices.

## 4. Internal Working

1. **Snapshot at load.** When `findById`/`save` puts an entity in the context, Hibernate stores the
   entity instance *and* a snapshot — a copy of its persistent field values at that moment.
2. **Mutation.** Your setters change the instance. The snapshot is deliberately **not** updated.
3. **Flush trigger.** Flush happens before the transaction commits (default `FlushMode.AUTO` also
   flushes before queries that might be affected). Spring's `@Transactional` commit is the flush
   point that matters here.
4. **Diff.** For each managed entity, Hibernate compares current values to the snapshot field by
   field. If none differ, no SQL. If some differ, it builds an UPDATE.
5. **SQL emission.** The UPDATE is sent (with `show-sql=true` you can watch it appear even though no
   `save()` exists in the Java code). After commit, the entity detaches and its snapshot is gone.

The prerequisites are strict: the entity must be **managed** and the code must run **inside an open
persistence context / transaction**. Remove either and dirty checking cannot fire.

## 5. Flow Diagram (ASCII)

```
 LOAD                         MUTATE                       FLUSH (at commit)
 ─────                        ───────                      ──────────────────
 findById(appointmentId)      appointment.setDoctor(doc)   for each managed entity:
     │                             │                          compare fields vs snapshot
     ▼                             ▼                                │
 instance:  {doctor = D_old}   instance: {doctor = D_new}      doctor changed?
 SNAPSHOT:  {doctor = D_old}   SNAPSHOT: {doctor = D_old} ───────► YES
     │                             │                                │
     └───── same at load ──────────┘                                ▼
                                                      UPDATE appointment SET doctor_id = D_new
                                                      WHERE id = appointmentId
                                             (no save() call anywhere in the Java code)
```

## 6. Real-world Analogy

A **shift nurse and a chart photocopy**. When a patient's chart is opened, a photocopy of its
current state is stapled to the back (the snapshot). All shift, the nurse writes updates on the live
chart, never on the photocopy. At end of shift (flush), a clerk lays the live chart next to its
photocopy, spots exactly which lines changed, and records only those into the permanent ledger. The
nurse never fills out an "update form" — changing the chart *is* the instruction. But if the nurse
takes the chart home after the shift ends (detached), no clerk is there to compare it, so nothing
gets recorded no matter how much they scribble.

## 7. How THIS PROJECT Uses It

`AppointmentService.reAssignAppointmentToAnotherDoctor` (`service/AppointmentService.java`) is the
**canonical** dirty-checking example in this codebase and is worth memorizing:

- It is `@Transactional`, so a persistence context is open for the whole method.
- `appointmentRepository.findById(appointmentId)` returns a **managed** `Appointment` with a snapshot.
- `appointment.setDoctor(doctor)` changes one field. **There is no `save()` call** — the in-code
  comment literally says *"this will automatically call the update, because it is dirty."*
- At commit, Hibernate diffs the appointment against its snapshot, sees `doctor` changed, and emits
  the UPDATE.

Two more places lean on the same mechanism:

- `DoctorService.onBoardNewDoctor` — `user.getRoles().add(RoleType.DOCTOR)` mutates a managed `User`
  loaded via `findById`; the new role is persisted by dirty checking on the `@ElementCollection`,
  with no `userRepository.save(user)`.
- `InsuranceService.assignInsuranceToPatient` / `disaccociateInsuranceFromPatient` — setting
  `patient.setInsurance(...)`/`(null)` on the managed `patient` is persisted through dirty checking
  (with cascade/orphanRemoval doing the child insert/delete), again with no explicit repository call
  on `Patient`.

## 8. Code Example From This Project

```java
// service/AppointmentService.java
@Transactional
@PreAuthorize("hasAuthority('appointment:write') or #doctorId == authentication.principal.id")
public Appointment reAssignAppointmentToAnotherDoctor(Long appointmentId, Long doctorId) {
    Appointment appointment = appointmentRepository.findById(appointmentId).orElseThrow();
    Doctor doctor = doctorRepository.findById(doctorId).orElseThrow();

    // No explicit save() call here. Because this method is @Transactional and `appointment` was
    // loaded via findById (so it's a managed entity attached to the persistence context), Hibernate
    // compares its current state to the snapshot taken at load time when the transaction flushes/
    // commits, notices doctor changed, and issues the UPDATE itself - this is dirty checking.
    appointment.setDoctor(doctor); // this will automatically call the update, because it is dirty

    doctor.getAppointments().add(appointment); // just for bidirectional consistency

    return appointment;
}
```

## 9. Line-by-Line Explanation

- `@Transactional` — the enabling condition. It opens the context that keeps `appointment` managed
  and defines the commit-time flush where the diff runs. Without it, dirty checking cannot fire.
- `appointmentRepository.findById(appointmentId).orElseThrow()` — loads and **snapshots** the
  appointment; this instance is now managed.
- `doctorRepository.findById(doctorId).orElseThrow()` — loads the new doctor (also managed); needed
  so the FK points at a real, persistent row.
- `appointment.setDoctor(doctor)` — the *only* change. It diverges the instance from its snapshot;
  everything else about the appointment stays equal, so the emitted UPDATE touches just the
  `doctor_id` column.
- `doctor.getAppointments().add(appointment)` — in-memory graph consistency; the FK is on
  `Appointment`, so this changes nothing on disk and is not what triggers the UPDATE.
- `return appointment` — returns the entity; after commit the UPDATE has already been flushed and
  the returned instance is detached.

## 10. Common Mistakes

Dirty checking silently does nothing when its prerequisites are missing — these are the ways this
codebase's patterns can be broken:

- **Detached entity.** Mutating the `Appointment` returned from `reAssignAppointmentToAnotherDoctor`
  *after* the method returns (in the controller) produces no UPDATE — it's detached, no snapshot, no
  context.
- **No transaction.** Doing the same load-mutate outside any `@Transactional` boundary: the entity
  detaches when the implicit read finishes, so the later setter is not tracked. (This is why the
  mutation methods here are all `@Transactional`.)
- **Bulk `@Modifying` update bypasses it entirely.** `PatientRepository.updateNameWithId`
  (`repository/PatientRepository.java`) is `@Modifying @Query("UPDATE Patient p SET p.name = :name
  where p.id = :id")`. It writes straight to the database *without* loading or snapshotting anything,
  so no dirty checking or entity listeners run — and, worse, if a `Patient` with that id is **already
  managed** in the current context, that in-memory instance is now **stale** (still holds the old
  name) until it is reloaded/refreshed, because the bulk update never touched the identity map.
- **Expecting `save()` to be required.** Adding `appointmentRepository.save(appointment)` to
  `reAssignAppointmentToAnotherDoctor` would be redundant for a managed entity — the context already
  flushes the change.

## 11. Best Practices

- Load, mutate, and let flush do the write — inside one transaction. Don't sprinkle unnecessary
  `save()` calls on already-managed entities.
- After a bulk `@Modifying` update, either avoid using any entity you loaded before it, or
  reload/refresh — never trust a pre-loaded instance's fields post-bulk-update.
- Map to a DTO before returning so the caller can't accidentally mutate a detached entity and expect
  persistence (the near-universal pattern here; `reAssignAppointmentToAnotherDoctor` returning the
  raw entity is the noted exception).
- Keep transactions focused: fewer managed entities means a cheaper flush-time diff.

## 12. Performance Notes

- **Flush scans everything managed.** The diff runs over every entity in the context, changed or
  not. A context loaded with hundreds of read-only entities pays that scan cost for zero writes —
  prefer projections (`countEachBloodGroupType`) or short transactions for read-heavy paths.
- **Column-level minimal UPDATEs.** Hibernate updates only changed columns (default dynamic-update
  behavior varies, but the diff is always column-aware), so reassigning a doctor rewrites `doctor_id`
  rather than the whole appointment row.
- **Bulk updates trade tracking for speed.** `updateNameWithId` rewrites matching rows in one
  statement with no per-entity overhead — fast, but you forfeit dirty checking, listeners, and
  cache/identity-map coherence.

## 13. Interview Questions

- **Q: How does Hibernate know an entity changed without a `save()` call?**
  A: It compares the managed entity's current field values against the snapshot taken at load and
  emits an UPDATE at flush for any difference — dirty checking; see
  `reAssignAppointmentToAnotherDoctor`.
- **Q: What two conditions must hold for dirty checking to fire?**
  A: The entity must be managed (in an open context) and the code must run inside that
  context/transaction.
- **Q: Why can a bulk `@Modifying` update leave loaded entities stale?**
  A: It writes directly to the DB and never updates the persistence context / identity map, so any
  already-loaded instance keeps its old values until refreshed — exactly the trap noted on
  `PatientRepository.updateNameWithId`.
- **Q: Does calling `save()` on a managed entity do anything extra?**
  A: No — the change is already flushed by dirty checking; the `save()` is redundant.

## 14. Summary

Dirty checking lets this project mutate entities as plain objects and get UPDATEs for free:
Hibernate snapshots each managed entity at load and diffs it at flush.
`AppointmentService.reAssignAppointmentToAnotherDoctor` is the textbook case — a managed
`Appointment`, one setter, no `save()`, one UPDATE. It only works for managed entities inside a
transaction, which is why detaching an entity, dropping the `@Transactional`, or using the bulk
`PatientRepository.updateNameWithId` (which bypasses the context and staleness-poisons any loaded
`Patient`) all defeat it.
