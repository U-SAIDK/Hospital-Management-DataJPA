# Pagination & Sorting

## 1. Definition

Pagination is the practice of returning a large result set in small, bounded chunks ("pages")
instead of all at once. Spring Data JPA models this with three cooperating types: `Pageable`
(a request for "page N of size M, sorted by X"), `Sort` (an ordering specification on its own),
and `Page<T>` (the returned slice plus metadata — total element/page counts). You never write
`LIMIT`/`OFFSET`/`ORDER BY` by hand; you pass a `Pageable` into a repository method and Spring Data
appends the SQL for you — even when the underlying query is raw native SQL.

## 2. Core Idea

```
PageRequest.of(pageNumber, pageSize[, Sort])   →   Pageable   →   repository method
                                                                        │
                                             Spring Data appends LIMIT/OFFSET (+ ORDER BY)
                                                                        │
                                                                        ▼
                                                   Page<T>  =  content slice
                                                             +  total element/page counts
                                                                (computed by a second COUNT query)
```

- **`Pageable`** — the interface describing the slice you want. `PageRequest.of(...)` is the usual
  concrete factory.
- **`Sort`** — an ordering (e.g. `Sort.by("name")`, ascending by default). Can be built standalone
  or folded into a `PageRequest`.
- **`Page<T>`** — the result. It carries the page's content *and* the total row count, unlike a plain
  `List<T>` which is just the rows.

## 3. Why We Need It

`AdminController.getAllPatients` exposes `page`/`size` request params. Without pagination it would
call something like `findAll()` and serialize every patient row in the database into one JSON
response — unbounded memory on the server, an unbounded payload on the wire, and an unbounded
`SELECT` on the DB. Pagination caps all three: the DB only scans/returns one page, Hibernate only
hydrates one page of entities, and the client only receives one page. Sorting makes those pages
deterministic and navigable (page 2 means the same rows every time only if there is a stable order).

## 4. Internal Working

When a repository method takes a `Pageable` (and/or returns `Page<T>`), Spring Data's proxy:

1. Reads `pageNumber`, `pageSize`, and any `Sort` off the `Pageable`.
2. Appends `LIMIT pageSize OFFSET pageNumber*pageSize` (and `ORDER BY` for the `Sort`) to the query
   before handing it to Hibernate — **this happens for native queries too**, not just JPQL. In
   `PatientRepository.findAllPatients` the written SQL is only `select * from patient`; the
   `LIMIT`/`OFFSET` are supplied by Spring Data from the `Pageable`, never appear in the source.
3. If the return type is `Page<T>` (as opposed to `Slice<T>` or `List<T>`), it runs a **second,
   separate `COUNT` query** to compute `getTotalElements()`/`getTotalPages()`. This is the extra cost
   of `Page`: two round trips per call (one for the page, one for the count).

`PatientService.getAllPatients` builds the `Pageable` and calls the method:

```java
// service/PatientService.java
public List<PatientResponseDto> getAllPatients(Integer pageNumber, Integer pageSize) {
    return patientRepository.findAllPatients(PageRequest.of(pageNumber, pageSize))
            .stream()
            .map(patient -> modelMapper.map(patient, PatientResponseDto.class))
            .collect(Collectors.toList());
}
```


## 6. Real-world Analogy

A search-results screen. You never get all ten thousand hits dumped on you — you get "results 1–10
of 8,432, page 1 of 844." The `10` is `pageSize`, the `1` is the (1-based, human-facing) page, the
`8,432` and `844` are `getTotalElements()`/`getTotalPages()` — and computing those totals requires the
system to count everything once (the second COUNT query), which is why some sites show "page 1 of
many" instead: they skipped the count to save a query (that's `Slice`, below).

## 7. How THIS PROJECT Uses It

Pagination appears in exactly one production path and one test:

- **Repository** — `PatientRepository.findAllPatients(Pageable pageable)` is a **native** query
  returning `Page<Patient>`:

```java
// repository/PatientRepository.java
@Query(value = "select * from patient", nativeQuery = true)
Page<Patient> findAllPatients(Pageable pageable);
```

- **Service** — `PatientService.getAllPatients(pageNumber, pageSize)` wraps the ints into
  `PageRequest.of(pageNumber, pageSize)` (no `Sort`) and passes it in.
- **Controller** — `AdminController.getAllPatients` supplies the page/size from request params,
  defaulting to `page=0`, `size=10`.
- **Test / exploration** — `PatientTests.testTransactionMethods` calls the same method with a
  sorted, second-page request:

```java
// test/.../PatientTests.java
Page<Patient> patientList = patientRepository.findAllPatients(PageRequest.of(1, 2, Sort.by("name")));
```

## 9. Line-by-Line Explanation

- `PageRequest.of(1, 2, Sort.by("name"))` — **page index 1** (page indices are **0-based**, so this
  is the *second* page, not the first), **page size 2**, **sorted by the `name` field ascending**.
  Spring Data turns this into `... ORDER BY name ASC LIMIT 2 OFFSET 2` appended onto
  `select * from patient`.
- `Sort.by("name")` — note the argument is the **entity field name** (`name`), which happens to match
  the column here; for a native query the name still has to resolve to a real selectable column.
- `for (Patient patient : patientList)` — `Page<Patient>` implements `Iterable`, so you can loop it
  directly; iterating yields only that page's content, not the whole table.
- `PageRequest.of(pageNumber, pageSize)` in the service — **no `Sort` argument**, so the page order
  is whatever the DB returns (undefined without an `ORDER BY`); a real gap for stable paging.
- `.stream().map(... PatientResponseDto ...).collect(...)` — the service immediately **discards the
  `Page` wrapper**, keeping only the content as a `List<PatientResponseDto>`. All the
  `getTotalElements()`/`getTotalPages()`/`hasNext()` metadata (which cost that extra COUNT query to
  compute) is thrown away before the controller ever sees it — see Common Mistakes.

## 10. Common Mistakes

- **Off-by-one on the page index.** `PageRequest.of(1, 2, ...)` is the **second** page, because
  page indices start at 0. The test's `PageRequest.of(1, 2, ...)` skips the first two rows. Expecting
  it to be "page one / the first two rows" is the classic mistake.
- **Paying for `Page` metadata, then throwing it away.** `PatientService.getAllPatients` returns a
  `List<PatientResponseDto>` — it triggers the extra COUNT query that `Page` requires, then discards
  `getTotalElements()`/`getTotalPages()` entirely. If the client never needs totals, this is a wasted
  query on every call (use `Slice`, or return the `Page` and actually forward the metadata).
- **Paging without sorting.** `PatientService`'s `PageRequest.of(pageNumber, pageSize)` has no `Sort`,
  so "page 2" is not guaranteed to be disjoint from "page 1" — without a stable `ORDER BY`, the DB may
  return rows in a different order between calls, causing skipped/duplicated rows across pages.
- **Unbounded page size.** Nothing here caps `size`; a client can request `size=1000000` and defeat
  the point of pagination. There is no server-side max-page-size guard in this project.
- **Sorting on an unindexed column.** `Sort.by("name")` sorts `Patient` by `name`, but `Patient`'s
  only index is on `birthDate` (`idx_patient_birth_date`, see `entity/Patient.java`). Large sorts on
  `name` cannot use an index and force a full sort.

## 11. Best Practices

- **Cap the maximum page size server-side** (e.g. clamp `size` to some ceiling). Not done in this
  project — flag as a gap, not a pattern to copy.
- **Always supply a stable `Sort`** (ideally on an indexed, unique-ish column) when paging, so pages
  are deterministic. This project's production call omits it.
- **Prefer `Slice<T>` over `Page<T>` when you don't need the total count** — `Slice` skips the second
  COUNT query and only tells you whether a next page exists (`hasNext()`), which is enough for
  infinite-scroll style UIs. This project always uses `Page` (via `findAllPatients`) even though the
  service discards the totals — the exact situation where `Slice` would have been cheaper.
- **Keep the `Pageable` out of the entity/DTO layer** — build it at the service boundary from
  primitive params (as `PatientService` does from `pageNumber`/`pageSize`), so controllers stay
  ignorant of Spring Data types.

## 12. Performance Notes

- **`Page` = two queries per call.** One `SELECT ... LIMIT ... OFFSET ...` for the content, plus one
  `SELECT COUNT(*)` for the totals. On a hot endpoint that count can dominate. `Slice`/`List` avoid it.
- **`OFFSET` gets slower as you page deeper.** `OFFSET 100000` still makes the DB walk and discard
  100,000 rows. Deep pagination is a known anti-pattern; keyset ("seek") pagination avoids it, but
  isn't used here.
- **Native + `Page` still works, but Spring Data must derive the count query** from your native SQL;
  for simple `select * from patient` it does so automatically. Complex native queries sometimes need
  an explicit `countQuery` — not needed here because the base query is trivial.
- Turn on `spring.jpa.show-sql=true` (already set in `application.properties`) to see both the paged
  `SELECT` *and* the separate `COUNT` fired by a single `findAllPatients` call.

## 13. Interview Questions

- Q: What's the difference between `Page<T>` and `List<T>` as a repository return type?
  A: `List<T>` is just the rows for that page. `Page<T>` adds metadata — `getTotalElements()`,
  `getTotalPages()`, `hasNext()`, etc. — which Spring Data computes by running an **extra COUNT
  query**. `List` (or `Slice`) skips that second query.
- Q: Does Spring Data apply `LIMIT`/`OFFSET` to a **native** query?
  A: Yes. `PatientRepository.findAllPatients` is `@Query(nativeQuery = true)` with only
  `select * from patient`, yet passing a `Pageable`/returning `Page<Patient>` makes Spring Data
  append the pagination SQL (and run a COUNT) itself.
- Q: In `PageRequest.of(1, 2, Sort.by("name"))`, which rows come back?
  A: The 3rd and 4th rows in `name`-ascending order — page **index 1** (0-based) means the second
  page, size 2.
- Q: `PatientService.getAllPatients` returns a `List`, not a `Page`. What's the cost?
  A: It still triggers the `Page` COUNT query (the repo method returns `Page`), then discards the
  metadata — a wasted query. `Slice` would have been cheaper if totals aren't needed.

## 14. Summary

This project paginates in one place: `PatientRepository.findAllPatients` — a **native** query that
nonetheless gets `LIMIT`/`OFFSET`/`ORDER BY` from the `Pageable` Spring Data hands it, and (because it
returns `Page<Patient>`) an extra COUNT query for the totals. `PatientService.getAllPatients` builds
that `Pageable` via `PageRequest.of(pageNumber, pageSize)` from `AdminController`'s request params,
then throws the `Page` metadata away — a missed opportunity that would have been cheaper as a `Slice`.
`PatientTests.testTransactionMethods` shows the sorted, 0-based-index form,
`PageRequest.of(1, 2, Sort.by("name"))`. Key takeaways: page indices are 0-based, `Page` costs a
second COUNT query, and pagination without a stable `Sort` gives non-deterministic pages. See
`NOTES/04`/`NOTES/05` for query-method vs JPQL vs native basics, and `NOTES/14` for the N+1 angle on
fetching per page.
