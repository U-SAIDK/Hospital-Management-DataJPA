# Lazy vs Eager Loading

## 1. Definition

**Fetch type** decides *when* an entity's association is loaded from the database:

- **EAGER** — the association is loaded immediately, in the same query (or an extra query) that loads
  the owning entity.
- **LAZY** — the association is left as a Hibernate **proxy** (a stand-in object) and only loaded on
  first real access, and only if the persistence context is still open.

In JPA the defaults depend on the mapping cardinality: `@ManyToOne` and `@OneToOne` default to
**EAGER**; `@OneToMany` and `@ManyToMany` default to **LAZY**. Either default can be overridden with
`fetch = FetchType.X`.

## 2. Core Idea

LAZY buys you cheaper loads (don't fetch what you don't touch) at the cost of needing an open context
when you finally touch it. EAGER buys you always-available data at the cost of always paying for it,
even when unused. This project deliberately mixes all four combinations so you can see both the SQL
each produces and the failure mode LAZY introduces.

## 3. Why We Need It

- Fetching everything eagerly turns one entity load into a cascade of joins and can pull huge object
  graphs you never use.
- Fetching everything lazily risks `LazyInitializationException` when code accesses an association
  after its transaction ended.
- Choosing per-association lets you fetch the common-path data eagerly and defer the rest — the
  central performance/correctness trade-off in JPA.

## 4. Internal Working

- **EAGER `@ManyToOne`/`@OneToOne`** — Hibernate typically adds a JOIN (or issues a follow-up SELECT)
  so the associated row is materialized as a real entity right away.
- **LAZY `@ManyToOne`** — Hibernate stores a **proxy**: a generated subclass holding only the FK/id.
  The first call to a real getter (`getName()`) triggers a SELECT to initialize it — *if* the context
  is open. If the owning entity has since detached, that access throws
  `LazyInitializationException`.
- **LAZY `@OneToMany`/`@ManyToMany`** — the collection is a lazy wrapper; iterating or sizing it
  triggers the load, again only while the context is open.
- **EAGER `@OneToMany`** — the collection is populated at load time (extra SELECT / join).

The prerequisite for *any* lazy initialization is an **open persistence context**. In this project
that means: inside the `@Transactional` service method that loaded the entity. There is no
`OpenEntityManagerInViewFilter` override in the code, so lazy access outside that boundary is unsafe.

## 5. Flow Diagram (ASCII)

```
 LAZY @ManyToOne (Appointment.doctor)
 ─────────────────────────────────────
   findById(appointment) ──► SELECT appointment           (doctor = PROXY, no SQL yet)
        │
        │  ── inside tx ──►  appointment.getDoctor().getName()
        │                        └─► SELECT doctor ...      (proxy initializes) ✅
        │
        └─ tx commit → detached
                          appointment.getDoctor().getName()
                              └─► LazyInitializationException ❌ (no open context)

 EAGER @ManyToOne (Appointment.patient)
 ──────────────────────────────────────
   findById(appointment) ──► SELECT appointment JOIN patient  (patient = real entity, loaded now)
        │
        └─ tx commit → detached
                          appointment.getPatient().getName()  ✅ (already loaded, no lazy access)
```

## 6. Real-world Analogy

EAGER is a restaurant that brings your **main course and every possible side** the moment you order —
nothing to wait for later, but you pay for and carry sides you may never eat. LAZY is bringing the
main course with a **buzzer** for each side; press it and the side is cooked to order — efficient if
you skip most sides, but the kitchen only honors buzzers *while the restaurant is open*. Press a
buzzer after closing time (context detached) and you get nothing but an error — that's
`LazyInitializationException`.

## 7. How THIS PROJECT Uses It

The codebase sets up a deliberate 2×2 teaching contrast across two entities:

| Association | Declared fetch | JPA default for its type | Effect |
|---|---|---|---|
| `Appointment.doctor` | **explicit LAZY** (`@ManyToOne(fetch = FetchType.LAZY)`) | EAGER | proxy until accessed |
| `Appointment.patient` | **default EAGER** (`@ManyToOne`, no override) | EAGER | loaded with the appointment |
| `Patient.appointments` | **explicit EAGER** (`fetch = FetchType.EAGER`) | LAZY | collection loaded up front |
| `Doctor.appointments` | **default LAZY** (`@OneToMany`, no override) | LAZY | collection loaded on access |

- `entity/Appointment.java` — `patient` is a plain `@ManyToOne` (EAGER default), `doctor` is
  `@ManyToOne(fetch = FetchType.LAZY)`. So loading an `Appointment` always brings its `Patient`, but
  its `Doctor` stays a proxy until touched. Both fields are `@ToString.Exclude` precisely so a
  `toString()` won't force the lazy proxy to initialize or recurse.
- `entity/Patient.java` — `appointments` is `@OneToMany(..., fetch = FetchType.EAGER)`, overriding the
  usual LAZY default for collections; the comment marks it explicitly as a teaching contrast, not a
  universally correct choice.
- `entity/Doctor.java` — `appointments` is `@OneToMany(mappedBy = "doctor")` with no fetch, i.e. the
  LAZY default.

Where it matters in services:

- `AppointmentService.getAllAppointmentsOfDoctor` accesses `doctor.getAppointments()` — Doctor's LAZY
  collection — but does so **inside** the `@Transactional`-free method while the (short) read context
  is still active and maps to DTOs immediately, so it initializes fine and never leaks a proxy.
- `AppointmentService.reAssignAppointmentToAnotherDoctor` **returns the raw `Appointment` entity**.
  Because `Appointment.doctor` is LAZY, if the controller then calls `appointment.getDoctor()...` the
  context is already closed and it throws `LazyInitializationException`. This is the concrete lazy
  risk in the codebase — everywhere else, services map to DTOs *before* returning, sidestepping it.
- `PatientRepository.findAllPatientWithAppointment` uses `LEFT JOIN FETCH p.appointments` to load the
  collection in one query — the explicit fetch-join tool for controlling fetching regardless of the
  mapping's default.

## 8. Code Example From This Project

```java
// entity/Appointment.java
// No explicit fetch here: @ManyToOne defaults to EAGER, so patient loads immediately with the
// Appointment (contrast with doctor below, which opts into LAZY).
@ManyToOne
@ToString.Exclude
@JoinColumn(name = "patient_id", nullable = false)
private Patient patient;

// Explicitly LAZY: doctor is loaded as a Hibernate proxy until actually accessed, avoiding an
// extra join/query whenever an Appointment is fetched but the doctor's own fields aren't needed.
@ManyToOne(fetch = FetchType.LAZY)
@ToString.Exclude
@JoinColumn(nullable = false)
private Doctor doctor;
```

```java
// entity/Patient.java — explicit EAGER, overriding the LAZY default for collections
@OneToMany(mappedBy = "patient", cascade = {CascadeType.REMOVE}, orphanRemoval = true, fetch = FetchType.EAGER)
private List<Appointment> appointments = new ArrayList<>();
```

```java
// entity/Doctor.java — default LAZY for @OneToMany
@OneToMany(mappedBy = "doctor")
private List<Appointment> appointments = new ArrayList<>();
```

## 9. Line-by-Line Explanation

- `@ManyToOne` on `patient` (no `fetch`) — inherits the EAGER default, so every `SELECT appointment`
  also materializes its `Patient`; safe to access after the context closes because it's already
  loaded.
- `@ManyToOne(fetch = FetchType.LAZY)` on `doctor` — overrides the default to LAZY; loading an
  appointment leaves `doctor` a proxy and skips the doctor query until a getter is called — a saving
  when the doctor's fields aren't needed.
- `@ToString.Exclude` on both — prevents a generated `toString()` from initializing the lazy `doctor`
  proxy or recursing through `patient` → `patient.appointments`.
- `Patient.appointments` `fetch = FetchType.EAGER` — forces the collection to load with the patient
  (opposite of the LAZY default); chosen here as a deliberate contrast, and it's why loading a
  `Patient` also pulls its appointments.
- `Doctor.appointments` (no fetch) — LAZY default; the collection loads only when accessed within an
  open context, as in `getAllAppointmentsOfDoctor`.

## 10. Common Mistakes

- **Accessing a LAZY association after the transaction closes.** The canonical trap here: using the
  `Appointment` returned by `reAssignAppointmentToAnotherDoctor` and calling `getDoctor()` in the
  controller → `LazyInitializationException`.
- **Assuming `@ManyToOne` is lazy.** It defaults to **EAGER**; `Appointment.patient` is always
  fetched even when unused.
- **Assuming `@OneToMany` is eager.** It defaults to **LAZY**; `Doctor.appointments` won't be there
  outside an open context unless fetched.
- **Serializing entities to JSON directly.** Jackson touching a lazy proxy on a detached entity
  triggers the same exception — one more reason this project maps to DTOs inside the context.
- **Making everything EAGER to "avoid" the exception.** That fixes the symptom by permanently paying
  for data you may not use, and can explode into large joins / N+1.

## 11. Best Practices

- Default associations to **LAZY** and fetch what you need explicitly (`JOIN FETCH`, as in
  `findAllPatientWithAppointment`) — the general recommendation, even though this project keeps some
  EAGER mappings for teaching.
- Map entities to DTOs **inside** the transaction (the dominant pattern here) so no lazy proxy ever
  escapes to a detached context.
- Exclude lazy/bidirectional associations from `toString()` (as `Appointment` does) to avoid
  accidental initialization and recursion.
- Reserve EAGER for associations you truly always need with the parent, and measure the resulting
  SQL with `show-sql=true`.

## 12. Performance Notes

- **EAGER `Patient.appointments`** means every `Patient` load also loads all appointments — fine for
  one patient, but calling `findAll()` over many patients this way can be heavy; `JOIN FETCH`
  (`findAllPatientWithAppointment`) at least collapses it into a single query instead of N+1.
- **LAZY `Appointment.doctor`** avoids a doctor SELECT/join whenever the doctor's fields aren't used
  — a real saving on read-heavy appointment listings.
- **N+1 risk** appears when iterating a collection of parents and touching a LAZY association per
  element; the fix is a fetch-join or an EAGER mapping, chosen deliberately. Watch the generated SQL
  to tell which path you're on.
- Combining multiple collection fetch-joins can multiply rows or throw `MultipleBagFetchException`
  (the commented-out second `JOIN FETCH a.doctor` in `PatientRepository` notes exactly this caution).

## 13. Interview Questions

- **Q: What are the JPA default fetch types per association?**
  A: `@ManyToOne`/`@OneToOne` → EAGER; `@OneToMany`/`@ManyToMany` → LAZY. This project overrides two
  of them (`Appointment.doctor` → LAZY, `Patient.appointments` → EAGER).
- **Q: When exactly does `LazyInitializationException` occur?**
  A: When a lazy association is accessed after its persistence context has closed (entity detached) —
  e.g. `getDoctor()` on the entity returned by `reAssignAppointmentToAnotherDoctor` in the controller.
- **Q: How do you load a lazy association without making the mapping EAGER?**
  A: A `JOIN FETCH` query (`findAllPatientWithAppointment`), or access it within the open transaction
  and map to a DTO.
- **Q: Why are `Appointment`'s associations `@ToString.Exclude`?**
  A: To stop `toString()` from initializing the lazy `doctor` proxy or recursing through the
  bidirectional `patient` graph.

## 14. Summary

Fetch type controls *when* associations load: EAGER now, LAZY on first access with an open context.
JPA defaults `@ManyToOne`/`@OneToOne` to EAGER and `@OneToMany`/`@ManyToMany` to LAZY, and this
project intentionally overrides two of them to teach the 2×2: `Appointment.doctor` (LAZY) vs
`Appointment.patient` (EAGER), and `Patient.appointments` (EAGER) vs `Doctor.appointments` (LAZY).
LAZY's payoff is skipping unneeded SQL; its hazard is `LazyInitializationException` after the context
closes — concretely realized by the raw-entity return of `reAssignAppointmentToAnotherDoctor`, and
avoided everywhere else by mapping to DTOs inside the transaction.
