# Performance & the N+1 Problem

## 1. Definition

The **N+1 problem** is the situation where fetching a list of N parent rows triggers 1 query for the
parents plus N additional queries — one per parent — to load an associated collection or relation.
The total is `N+1` SQL statements where a single well-formed `JOIN` would have done the job in one.
It is the single most common ORM performance bug, and it is easy to introduce accidentally because
the extra queries are fired *by Hibernate, transparently*, not by any code you can see.

## 2. Core Idea

```
findAll()  → SELECT * FROM patient                     (1 query, returns N patients)
             then, for EACH patient, to load appointments:
             SELECT * FROM appointment WHERE patient_id = ?   (N queries)
             ─────────────────────────────────────────────────
             total = N + 1 queries

findAllPatientWithAppointment()
             → SELECT p.*, a.* FROM patient p LEFT JOIN appointment a ...   (1 query)
```

The fix is almost always to fetch the association **in the same query** via `JOIN FETCH` (or an
entity graph). Whether the association is declared `LAZY` or `EAGER` does **not** decide whether N+1
happens — it only decides *when* the extra queries fire (on first access vs immediately at load).

## 3. Why We Need It (to understand)

This project deliberately configures `Patient.appointments` as `EAGER` (see below), which means a
plain `findAll()` on patients **already** exhibits N+1 today. Understanding this is the difference
between a request that runs 1 query and one that runs 101 queries for 100 patients — same Java code,
wildly different DB load. `spring.jpa.show-sql=true` (set in `application.properties`) is the tool
that makes the difference visible.

## 4. Internal Working

Consider `patientRepository.findAll()`. `Patient.appointments` is declared:

```java
// entity/Patient.java
@OneToMany(mappedBy = "patient", cascade = {CascadeType.REMOVE}, orphanRemoval = true, fetch = FetchType.EAGER)
private List<Appointment> appointments = new ArrayList<>();
```

Because it is `EAGER`, Hibernate must populate every patient's `appointments` before returning. By
default it does this with a **secondary select per patient**: one `SELECT ... FROM patient` for the N
patients, then one `SELECT ... FROM appointment WHERE patient_id = ?` for each — exactly N+1. The
"EAGER" keyword did not avoid N+1; it only moved the extra queries *earlier* (they fire immediately at
load time instead of lazily on first `.getAppointments()` access).

Contrast `Doctor.appointments`:

```java
// entity/Doctor.java
@OneToMany(mappedBy = "doctor")            // no fetch override → defaults to LAZY
private List<Appointment> appointments = new ArrayList<>();
```

Here the collection is `LAZY`, so `doctorRepository.findAll()` fires just 1 query; the per-doctor
appointment queries only fire *if and when* you call `.getAppointments()` on each doctor — but if you
do that in a loop, you get the same N+1, just triggered lazily.

**The fix in this repo** is `findAllPatientWithAppointment`:

```java
// repository/PatientRepository.java
@Query("SELECT p FROM Patient p LEFT JOIN FETCH p.appointments")
List<Patient> findAllPatientWithAppointment();
```

`JOIN FETCH` tells Hibernate to load patients *and* their appointments in **one** SQL statement (a
single JOIN), regardless of the association's declared fetch type. `LEFT` (not `INNER`) keeps patients
who have zero appointments in the result.

## 5. Flow Diagram (ASCII)

```
── N+1 path ──────────────────────────────────────────────
patientRepository.findAll()          (Patient.appointments is EAGER)
   │
   ├─ SELECT * FROM patient                         ← 1 query, N rows
   ├─ SELECT * FROM appointment WHERE patient_id=1  ← query 2
   ├─ SELECT * FROM appointment WHERE patient_id=2  ← query 3
   └─ ... one per patient ...                       ← query N+1

── Fixed path ────────────────────────────────────────────
patientRepository.findAllPatientWithAppointment()
   │
   └─ SELECT p.*, a.*
      FROM patient p LEFT JOIN appointment a ON a.patient_id = p.id   ← 1 query total
```

## 6. Real-world Analogy

You want the roster of 30 students and each student's list of enrolled courses. N+1 is walking to the
records office, asking "give me the 30 students," then walking back 30 more times, once per student,
to ask "now what courses is *this* one taking?" — 31 trips. `JOIN FETCH` is asking once: "give me the
30 students *with* their courses attached." One trip. The walking (network/DB round trips), not the
reading, is what costs you.

## 7. How THIS PROJECT Uses It

- **The N+1 risk that exists today:** any finder returning `Patient` (e.g. the inherited `findAll()`)
  triggers per-patient appointment loads because `Patient.appointments` is `EAGER`. This is a real,
  present N+1 in the codebase, not a hypothetical.
- **The explicit fix:** `PatientRepository.findAllPatientWithAppointment()` uses `LEFT JOIN FETCH` to
  collapse it into one query. It is exercised (exploratorily) by `PatientTests.testPatientRepository`.
- **A LAZY collection accessed safely:** `AppointmentService.getAllAppointmentsOfDoctor` loads one
  `Doctor` then calls `doctor.getAppointments()` (LAZY) *inside* the method — fine because the
  persistence context is still open there. Doing this across *many* doctors in a loop would be an N+1,
  but the codebase does not currently do that (it's a "would be," not an "is").
- **The diagnostic tool:** `spring.jpa.show-sql=true` in `application.properties` — run
  `findAll()` vs `findAllPatientWithAppointment()` and count the SELECTs in the console.


## 9. Line-by-Line Explanation

- `SELECT p FROM Patient p` — selects the `Patient` entity (JPQL, entity name not table name).
- `LEFT JOIN FETCH p.appointments` — `FETCH` is the key word: it says "initialize `p.appointments` as
  part of *this* query," producing one JOINed SQL statement instead of N secondary selects. `LEFT`
  keeps patients with no appointments.
- Returns `List<Patient>` fully initialized — no lazy proxy, no N+1, regardless of the `EAGER`/`LAZY`
  declaration on the field.
- The commented `... LEFT JOIN FETCH a.doctor` line — would additionally fetch each appointment's
  doctor in the same query. It's left commented because chaining fetch-joins across multiple
  `List`-typed collections is what triggers Hibernate's `MultipleBagFetchException`, and each extra
  to-many fetch-join multiplies the row count (cartesian growth).
- `System.out.println(patientList)` in the test — the whole point is to run it with `show-sql=true`
  and confirm **one** SQL statement appears, vs a wall of per-patient SELECTs for plain `findAll()`.

## 10. Common Mistakes

- **Believing `EAGER` "fixes" N+1.** It does not. `Patient.appointments` is `EAGER` and *still* causes
  N+1 on `findAll()` — EAGER only changes *when* the extra queries fire (immediately), not *whether*.
- **Believing `LAZY` "causes" N+1.** LAZY by itself fires 1 query; N+1 only appears when you then
  touch the lazy association per-parent in a loop. The trigger is the access pattern, not the keyword.
- **Uncommenting multiple to-many `JOIN FETCH`es carelessly.** The commented deeper-fetch line in
  `PatientRepository` risks `MultipleBagFetchException` and row multiplication — hence it's left off.
- **Forgetting `DISTINCT` on a to-many fetch-join.** `LEFT JOIN FETCH p.appointments` returns one row
  per (patient, appointment) pair, so a patient with 3 appointments appears 3 times in the raw result
  — Hibernate de-duplicates entity references, but the query still returns the cartesian rows. This
  project's query has no `DISTINCT` — acceptable for a learning harness, worth knowing in production.
- **Not looking at the SQL.** N+1 is invisible in Java. Without `show-sql=true` (or a query counter)
  you won't notice 101 queries where 1 would do.

## 11. Best Practices

- **Fetch associations you know you'll traverse with `JOIN FETCH`** (as `findAllPatientWithAppointment`
  does) rather than relying on per-element lazy access in a loop.
- **Prefer LAZY as the default on associations, fetch explicitly per use case.** This project's
  `EAGER` on `Patient.appointments` is a *teaching contrast*, not a recommendation — EAGER on a
  to-many means every finder pays the fetch cost whether the caller needs appointments or not.
- **Consider `@EntityGraph`** as a declarative alternative to `JOIN FETCH` for choosing what to fetch
  per query. This project does **not** use `@EntityGraph` anywhere (stated so you don't assume it does).
- **Add `DISTINCT` (or dedup in app code) when fetch-joining a to-many** to avoid duplicate parent rows.
- **Keep the persistence context open while you access lazy fields** (via `@Transactional`, as
  `AppointmentService.getAllAppointmentsOfDoctor` does) — otherwise the lazy access throws
  `LazyInitializationException` instead of merely being slow.

## 12. Performance Notes

- N+1 turns a fixed 1-query operation into an O(N)-query one — the cost scales with row count, so it
  often passes tests on tiny seed data and melts production.
- The dominant cost is **round trips**, not rows: 101 tiny queries are far slower than 1 slightly
  larger JOINed query because each query pays network + parse + plan latency.
- `JOIN FETCH` trades round trips for wider rows (and possible cartesian duplication). For a single
  to-many like `p.appointments` that's a clear win; for several to-many collections at once it can
  explode row counts — which is exactly why the deeper-fetch variant is left commented.
- `spring.jpa.show-sql=true` is the zero-cost first diagnostic; for production, a query-count
  assertion or a tool like Hibernate statistics / datasource-proxy is more reliable than eyeballing.

## 13. Interview Questions

- Q: What is the N+1 problem?
  A: Fetching N parents in 1 query, then 1 extra query per parent to load an association — N+1 total
  where a JOIN would do 1. Example here: `findAll()` on patients + per-patient appointment loads.
- Q: `Patient.appointments` is `EAGER`. Does that avoid N+1?
  A: No. EAGER still issues a secondary select per patient; it only makes them fire immediately at
  load instead of lazily. The fix is `JOIN FETCH` (`findAllPatientWithAppointment`), not EAGER.
- Q: How does `findAllPatientWithAppointment` fix it?
  A: `SELECT p FROM Patient p LEFT JOIN FETCH p.appointments` loads patients and appointments in one
  JOINed SQL statement, so there are no secondary selects — independent of the field's fetch type.
- Q: How would you *detect* N+1 in this project?
  A: Enable `spring.jpa.show-sql=true` (already on) and count the SELECTs: `findAll()` shows 1 + N,
  `findAllPatientWithAppointment` shows exactly 1.
- Q: Why is the deeper double-`JOIN FETCH` line left commented?
  A: Fetch-joining multiple `List`/bag collections at once risks `MultipleBagFetchException` and
  multiplies rows (cartesian product).

## 14. Summary

N+1 is 1 parent query plus N per-parent association queries. In this project it is not hypothetical:
`Patient.appointments` is `EAGER`, so any `Patient` finder like `findAll()` fires the extra
per-patient appointment selects immediately — proving EAGER changes *when*, not *whether*, N+1
happens. The remedy is `PatientRepository.findAllPatientWithAppointment()`, whose
`LEFT JOIN FETCH p.appointments` collapses everything into one SQL statement; it's exercised in
`PatientTests.testPatientRepository`. `Doctor.appointments` (LAZY) shows the contrasting default.
`spring.jpa.show-sql=true` in `application.properties` is how you actually see it. For fetch-strategy
fundamentals see `NOTES/11. Lazy vs Eager Loading.md`; for the persistence-context boundary that makes
lazy access safe-or-not see `src/MASTER_NOTES.md` §6.
