# Entity Mapping

## 1. Definition

Entity mapping is the set of JPA/Hibernate annotations that declare how a plain Java class and its
fields correspond to a relational table and its columns. `@Entity` marks a class as a persistent
type; `@Table`, `@Id`, `@GeneratedValue`, `@Column`, `@Enumerated`, `@ElementCollection`, `@Index`,
and `@UniqueConstraint` refine exactly what schema Hibernate generates and how each field is read
from / written to a row.

## 2. Core Idea

An entity is the single source of truth for both the Java object model AND the database schema. In
this project `spring.jpa.hibernate.ddl-auto=create` means Hibernate reads these annotations at
startup and *generates* the DDL — the tables, columns, indexes, and constraints are whatever the
annotations say they are. So every mapping annotation is doing two jobs at once:

- **Runtime job** — how a row is turned into a `Patient`/`User` object and back (column names,
  enum encoding, which fields are eager/lazy).
- **Schema job** — what `CREATE TABLE` Hibernate emits (nullability, length, unique constraints,
  indexes, collection tables).

## 3. Why We Need It

Without explicit mapping you get Hibernate's defaults, which are frequently wrong for a real schema:
the table would be named after the class (`user` — a reserved word in PostgreSQL, which is exactly
why this project renames it to `app_user`), every String column would be unbounded, nothing would be
indexed, no unique constraints beyond `@Id` would exist, and enums would be stored as fragile
integer ordinals. Mapping annotations let the code state the schema contract precisely and keep it
version-controlled next to the logic that depends on it.

## 4. Internal Working

- **`@Entity` + `@Table`** — registers the class with the `EntityManagerFactory` at boot; `@Table`
  overrides the default table name and attaches table-level `indexes` / `uniqueConstraints`.
- **`@Id` + `@GeneratedValue(strategy = IDENTITY)`** — marks the primary key and tells Hibernate the
  DB generates it. IDENTITY maps to a PostgreSQL auto-increment (`BIGSERIAL`/identity column):
  Hibernate does NOT know the id until after the INSERT returns, so it cannot batch inserts across a
  transaction the way a SEQUENCE strategy could.
- **`@Column(nullable, unique, length)`** — becomes `NOT NULL`, a `UNIQUE` constraint, and
  `VARCHAR(n)` respectively in the generated DDL, and drives Hibernate's own null/length checks.
- **`@Enumerated(EnumType.STRING)`** — stores the enum *constant name* as text instead of its
  ordinal position. On read, Hibernate matches the stored string back to a constant by name.
- **`@ElementCollection`** — maps a collection of *non-entity* values (here an enum set) into a
  separate collection table keyed by the owner's id; there is no second entity/`@Id` involved.
- **`@Index` / `@UniqueConstraint`** — table-level metadata inside `@Table` that emits
  `CREATE INDEX` and multi-column `UNIQUE` constraints Hibernate could not infer from a single field.

## 5. Flow Diagram (ASCII)

```
 Startup (ddl-auto=create)
        │
        ▼
 Hibernate reads entity annotations
        │
        ├── @Entity/@Table(name=app_user, indexes=…) ──► CREATE TABLE app_user (…), CREATE INDEX idx_provider_id_provider_type
        ├── @Id @GeneratedValue(IDENTITY)             ──► id BIGINT GENERATED … AS IDENTITY PRIMARY KEY
        ├── @Column(nullable=false, length=40)        ──► name VARCHAR(40) NOT NULL
        ├── @Column(unique=true)                      ──► UNIQUE constraint on column
        ├── @UniqueConstraint(name,birthDate)         ──► UNIQUE (name, birthDate)
        ├── @Enumerated(STRING) bloodGroup            ──► blood_group VARCHAR  (stores 'O_POSITIVE')
        └── @ElementCollection Set<RoleType> roles    ──► separate collection table (user_id, roles)

 Runtime INSERT/SELECT
        │
        ▼
 Row  <──►  Entity object   (enum text <──► RoleType constant, FK <──► @MapsId id, etc.)
```

## 6. Real-world Analogy

The entity class is like a fully annotated architectural blueprint. `@Column(length=40)` is the
dimension written on the wall, `@UniqueConstraint` is a note saying "no two rooms may share this
exact address," `@Index` is a marker for "put a quick-access door here," and `@Enumerated(STRING)`
is a decision to label rooms by name ("Kitchen") instead of by number ("Room 3") so renumbering the
floor plan never makes an old label point at the wrong room. Hibernate is the builder that
constructs the actual building (schema) exactly from the blueprint.

## 7. How THIS PROJECT Uses It

- **`entity/User.java`** — `@Table(name = "app_user", indexes = { @Index(name =
  "idx_provider_id_provider_type", columnList = "providerId, providerType") })`. The rename avoids
  the reserved word `user`; the composite index exists specifically for the OAuth2 login path, which
  looks a user up by `(providerId, providerType)` (see `UserRepository.findByProviderIdAndProviderType`).
  `roles` is an `@ElementCollection(fetch = FetchType.EAGER)` of `RoleType` — a plain enum set, not a
  joined entity.
- **`entity/Patient.java`** — `@Table(name = "patient", uniqueConstraints = { @UniqueConstraint(name
  = "unique_patient_name_birthdate", columnNames = {"name", "birthDate"}) }, indexes = { @Index(name
  = "idx_patient_birth_date", columnList = "birthDate") })`. `bloodGroup` is `@Enumerated(EnumType.STRING)`,
  `createdAt` is `@CreationTimestamp @Column(updatable = false)`. Note the *commented-out*
  `unique_patient_email` constraint — an evolving-schema artifact left in place, not something to
  "fix."
- **`entity/type/BloodGroupType.java`**, **`RoleType.java`**, **`AuthProviderType.java`** — plain
  enums stored via `EnumType.STRING`. **`PermissionType.java`** is different: it carries a `permission`
  string field, but it is NOT persisted as a column — it is used only as a Spring Security authority
  string.

## 8. Code Example From This Project

```java
// entity/User.java
@Entity
@Table(name = "app_user", indexes = {
        @Index(name = "idx_provider_id_provider_type", columnList = "providerId, providerType")
})
public class User implements UserDetails {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @JoinColumn(unique = true, nullable = false)
    private String username;
    private String password;               // nullable: OAuth2-only accounts have no local password

    private String providerId;

    @Enumerated(EnumType.STRING)
    private AuthProviderType providerType;

    @ElementCollection(fetch = FetchType.EAGER)
    @Enumerated(EnumType.STRING)
    Set<RoleType> roles = new HashSet<>();
}
```

```java
// entity/Patient.java
@Entity
@Table(
        name = "patient",
        uniqueConstraints = {
//                @UniqueConstraint(name = "unique_patient_email", columnNames = {"email"}),
                @UniqueConstraint(name = "unique_patient_name_birthdate", columnNames = {"name", "birthDate"})
        },
        indexes = {
                @Index(name = "idx_patient_birth_date", columnList = "birthDate")
        }
)
public class Patient {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 40)
    private String name;

    private LocalDate birthDate;

    @Column(unique = true, nullable = false)
    private String email;

    @CreationTimestamp
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @Enumerated(EnumType.STRING)
    private BloodGroupType bloodGroup;
}
```

## 9. Line-by-Line Explanation

- `@Table(name = "app_user", …)` — without the rename Hibernate would target `user`, a PostgreSQL
  reserved keyword; the explicit name is a hard requirement here, not cosmetic.
- `@Index(name = "idx_provider_id_provider_type", columnList = "providerId, providerType")` — a
  single composite index over both columns in that order; it exists to make the OAuth2 two-field
  lookup a fast index scan instead of a full-table scan. Note `columnList` uses the *entity field*
  names because Hibernate maps them to the generated column names.
- `@GeneratedValue(strategy = GenerationType.IDENTITY)` — identical across all six entities; the DB
  assigns the id on INSERT, so `save()` must round-trip to the DB before the id is known.
- `@Column(unique = true, nullable = false)` on `Patient.email` — emits both a `UNIQUE` and a
  `NOT NULL` on the same column. Because this single-column unique already exists, the commented-out
  `unique_patient_email` table constraint would have been redundant — a good illustration of why it
  was dropped.
- `@UniqueConstraint(… columnNames = {"name", "birthDate"})` — a *composite* uniqueness rule that a
  per-field `@Column(unique=true)` cannot express: it forbids two patients sharing the *same name
  AND birth date pair*, while allowing name or birthDate to repeat individually.
- `@Enumerated(EnumType.STRING)` on `bloodGroup` — stores `"O_POSITIVE"` as text. Without it JPA
  defaults to `ORDINAL`, storing `6` (the zero-based position of `O_POSITIVE` in `BloodGroupType`).
- `@CreationTimestamp @Column(updatable = false)` — Hibernate stamps `createdAt` once on INSERT;
  `updatable=false` removes the column from every generated UPDATE so later edits can never overwrite it.
- `@ElementCollection(fetch = FetchType.EAGER) @Enumerated(EnumType.STRING) Set<RoleType> roles` —
  maps the enum set to a collection table; EAGER is mandatory here because `User.getAuthorities()`
  reads `roles` during authentication, potentially after the original persistence context has closed
  — a LAZY set would throw `LazyInitializationException` at that point.

## 10. Common Mistakes

- **Relying on the default `ORDINAL` enum mapping.** If someone later reorders `BloodGroupType`
  (e.g. inserts a constant before `O_POSITIVE`), every previously stored ordinal silently now means a
  *different* blood group — a data-corruption bug with no error. This project avoids it by using
  `EnumType.STRING` everywhere enums are persisted.
- **Forgetting to rename `user`.** Leaving the default table name would generate DDL that collides
  with the PostgreSQL reserved word and fails at startup.
- **Assuming `@Column(unique=true)` and a table `@UniqueConstraint` do the same thing.** The former
  is single-column; only a `@UniqueConstraint(columnNames={…})` can enforce a *multi-column* rule
  like `(name, birthDate)`.
- **Expecting `createdAt` to update.** With `updatable=false` it never changes after insert — using
  it as a "last modified" field would be wrong.

## 11. Best Practices

- Always use `@Enumerated(EnumType.STRING)` for persisted enums (as this project does for
  `BloodGroupType`, `AuthProviderType`, `RoleType`) — trade a few bytes per row for immunity to
  reordering and a self-documenting column.
- Give every `@Index` and `@UniqueConstraint` an explicit `name` (as here) so migrations and error
  messages reference a stable identifier instead of a Hibernate-generated hash.
- Set `length` on String columns that have a known bound (`name` = 40/100, `policyNumber` = 50) so
  the schema documents the real constraint rather than defaulting to `VARCHAR(255)`.
- Keep the `EnumType.STRING` decision consistent between `@Enumerated` field sites and the enum's own
  documentation — the enum files here even comment on it.

## 12. Performance Notes

- The `idx_provider_id_provider_type` and `idx_patient_birth_date` indexes turn the corresponding
  lookups/range scans (`findByProviderIdAndProviderType`, `findByBirthDateBetween`,
  `findByBornAfterDate`) into index scans; without them those would be sequential scans that get
  slower linearly as rows grow.
- `EnumType.STRING` costs a little more storage and comparison time than `ORDINAL` (text vs a small
  int), but the difference is negligible next to the safety it buys — and index lookups on the string
  are still efficient.
- `@ElementCollection(fetch = EAGER)` on `roles` means every `User` load also issues a second select
  against the roles collection table. For the security principal that is loaded once per request this
  is an acceptable, bounded cost; EAGER on a *large* element collection would be a performance
  problem.
- `@GeneratedValue(IDENTITY)` prevents JDBC insert batching (Hibernate needs each generated id
  immediately), so bulk-inserting many rows is slower than it would be under a SEQUENCE strategy —
  irrelevant at this project's scale.

## 13. Interview Questions

- Q: Why store enums as `STRING` instead of `ORDINAL`?
  A: ORDINAL stores the constant's position, so reordering the enum silently reassigns meaning to
  existing rows. STRING stores the name, which is reorder-proof and human-readable in the DB. This
  project uses STRING for `BloodGroupType`, `AuthProviderType`, and `RoleType`.
- Q: What is the difference between `@Column(unique=true)` and `@UniqueConstraint`?
  A: `@Column(unique=true)` is a single-column uniqueness rule; `@UniqueConstraint(columnNames={…})`
  can span multiple columns — e.g. `Patient`'s `(name, birthDate)` composite constraint.
- Q: Why is `User.roles` `@ElementCollection` and EAGER?
  A: `RoleType` is a plain enum, not an entity, so `@ElementCollection` maps it to a collection table
  rather than a join to another entity. EAGER is required because `getAuthorities()` reads the roles
  during authentication, possibly outside the original persistence context, where LAZY would throw.
- Q: What does `@GeneratedValue(strategy = IDENTITY)` imply for inserts?
  A: The database assigns the key on INSERT, so Hibernate learns the id only after the statement runs
  and cannot batch inserts the way a SEQUENCE allocator could.

## 14. Summary

Entity mapping annotations in this project do double duty: they define the Java object model and
generate the PostgreSQL schema (`ddl-auto=create`). `User` renames its table to `app_user`, indexes
`(providerId, providerType)` for OAuth2 lookups, and holds `roles` as an EAGER `@ElementCollection`.
`Patient` enforces a composite `(name, birthDate)` unique constraint, indexes `birthDate`, and
stamps `createdAt` immutably. Enums (`BloodGroupType`, `RoleType`, `AuthProviderType`) are all
persisted with `@Enumerated(EnumType.STRING)` to stay immune to reordering — the single most
important mapping decision in the entity layer.
