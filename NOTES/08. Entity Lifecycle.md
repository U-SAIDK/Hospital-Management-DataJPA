# Entity Lifecycle

## 1. Definition

Every JPA entity instance is, at any moment, in exactly one of four **lifecycle states** that
describe its relationship to the persistence context and the database row it may represent:

- **Transient (New)** — a plain Java object Hibernate has never heard of; no row, no tracking.
- **Managed (Persistent)** — bound to the current persistence context; changes are tracked and
  flushed automatically.
- **Detached** — was managed, but its persistence context has closed; it still holds data but is no
  longer tracked.
- **Removed** — scheduled for deletion; still in the context until flush turns it into a DELETE.

The transitions between these states are the whole story of how an object becomes a database row and
back again.

## 2. Core Idea

The same `Appointment` object can travel through several states in a single request: it starts as a
`builder()` result (transient), becomes managed the instant it is saved inside a transaction, and
turns detached the moment the transaction that owned it commits. Knowing *which* state an instance
is in tells you three practical things: whether mutating it will produce SQL, whether you can safely
touch a lazy association on it, and whether `save()` will do an INSERT or a MERGE.

## 3. Why We Need It

Bugs in JPA code almost always trace back to a wrong assumption about state:

- Mutating a **detached** entity and expecting an UPDATE (nothing happens — no context is tracking
  it).
- Touching a **LAZY** association on a **detached** entity (throws `LazyInitializationException`).
- Assuming `builder().build()` is already persisted (it is **transient** — no id, no row until
  `save()`).

Understanding the state model lets you reason about these instead of guessing, and it explains why
this project maps entities to DTOs *before* returning them from most service methods.

## 4. Internal Working

- **Transient → Managed:** `EntityManager.persist()` (called by Spring Data's `save()` when the
  `@Id` is null) inserts the entity into the context, assigns/records its identity, and schedules an
  INSERT.
- **Managed:** the context holds `(instance, snapshot)`. Field changes are diffed against the
  snapshot at flush and turned into UPDATEs (dirty checking).
- **Managed → Detached:** happens automatically when the context closes (transaction commit), or via
  `detach()`/`clear()`. The instance keeps its field values but loses its snapshot and its link to
  the context — future changes are invisible and lazy proxies can no longer initialize.
- **Detached → Managed:** `EntityManager.merge()` (called by `save()` when the `@Id` is already set)
  copies the detached state onto a managed instance.
- **Managed → Removed:** `EntityManager.remove()`, or automatically when an association marked
  `orphanRemoval=true` is nulled/cleared. A DELETE is scheduled and emitted at flush.

## 6. Real-world Analogy

A **hospital admission** models the same states. A walk-in with no chart is *transient* — a person,
but no record. Admit them and they become *managed*: they get a chart on the active board, every
observation is logged, and staff track changes live. Discharge them and the chart is filed — they're
*detached*: the record still exists, but nobody is watching them anymore, so anything they do at
home isn't recorded (mutating a detached entity does nothing). Order a record purge and it's
*removed*: marked for deletion, actually shredded at the next filing pass (flush). Re-admit a
discharged patient by re-opening their filed chart onto the board — that's `merge()`.

## 7. How THIS PROJECT Uses It

Each state has a concrete home in this codebase:

- **Transient** — `Appointment.builder().reason(...).appointmentTime(...).build()` in
  `AppointmentService.createNewAppointment` (`service/AppointmentService.java`): it has no id and no
  row until `appointmentRepository.save(appointment)` runs. Likewise
  `Doctor.builder()...build()` in `DoctorService.onBoardNewDoctor` and the `User`/`Patient` built in
  `AuthService.signUpInternal`.
- **Managed** — any entity from `findById`/`save` inside a `@Transactional` method: the `Patient`
  and `Doctor` in `createNewAppointment`, the `appointment` in
  `reAssignAppointmentToAnotherDoctor`, the `User` in `onBoardNewDoctor` (whose
  `getRoles().add(...)` persists via tracking, no `save`), the `patient` in the `InsuranceService`
  methods.
- **Detached** — `AppointmentService.reAssignAppointmentToAnotherDoctor` **returns the raw
  `Appointment` entity** (not a DTO). Once the method commits, that returned instance is detached in
  the controller. This is the single place in the codebase where a managed entity crosses back to a
  non-transactional caller — and `Appointment.doctor` is LAZY, so touching `appointment.getDoctor()`
  there risks `LazyInitializationException`. Contrast the pervasive DTO pattern:
  `createNewAppointment`, `getAllAppointmentsOfDoctor`, `getPatientById`, `getAllDoctors` all map to
  a `*ResponseDto` *inside* the transaction, so no detached entity is ever exposed.
- **Removed** — `InsuranceService.disaccociateInsuranceFromPatient` sets `patient.setInsurance(null)`;
  because `Patient.insurance` is `orphanRemoval=true`, the orphaned `Insurance` moves to the removed
  state and is DELETEd at flush, with no explicit `insuranceRepository.delete(...)`.

## 8. Code Example From This Project

```java
// service/AppointmentService.java  (states annotated in comments)
@Transactional
@Secured("ROLE_PATIENT")
public AppointmentResponseDto createNewAppointment(CreateAppointmentRequestDto createAppointmentRequestDto) {
    Long doctorId = createAppointmentRequestDto.getDoctorId();
    Long patientId = createAppointmentRequestDto.getPatientId();

    Patient patient = patientRepository.findById(patientId)         // MANAGED
            .orElseThrow(() -> new EntityNotFoundException("Patient not found with ID: " + patientId));
    Doctor doctor = doctorRepository.findById(doctorId)             // MANAGED
            .orElseThrow(() -> new EntityNotFoundException("Doctor not found with ID: " + doctorId));
    Appointment appointment = Appointment.builder()                // TRANSIENT
            .reason(createAppointmentRequestDto.getReason())
            .appointmentTime(createAppointmentRequestDto.getAppointmentTime())
            .build();

    appointment.setPatient(patient);
    appointment.setDoctor(doctor);
    patient.getAppointments().add(appointment); // to maintain consistency

    appointment = appointmentRepository.save(appointment);         // TRANSIENT -> MANAGED (INSERT)
    return modelMapper.map(appointment, AppointmentResponseDto.class); // entity never leaves as-is
}
```

## 9. Line-by-Line Explanation

- `patientRepository.findById(patientId)` / `doctorRepository.findById(doctorId)` — each returns a
  **managed** entity; both are now tracked and their lazy proxies can initialize while this method
  runs.
- `Appointment.builder()...build()` — a **transient** object: no `@Id` assigned (`IDENTITY`
  generation only fills it on INSERT), no row, not in the context.
- `appointment.setPatient(patient)` / `setDoctor(doctor)` — wires the transient appointment to two
  managed entities; harmless now, meaningful at save.
- `patient.getAppointments().add(appointment)` — in-memory graph consistency only; `patient` is
  managed but the FK lives on `Appointment`, so this line writes nothing itself.
- `appointmentRepository.save(appointment)` — `@Id` is null, so Spring Data calls `persist()`:
  **transient → managed**, INSERT scheduled, generated id assigned to the returned instance.
- `modelMapper.map(appointment, AppointmentResponseDto.class)` — copies data into a DTO *inside* the
  transaction, so the still-managed entity (with its lazy `doctor`) never leaves the service and can
  never become a detached-lazy trap for the caller.

## 10. Common Mistakes

- **Treating a builder result as persisted.** `Appointment.builder().build()` is transient; without
  `save()` it is never written.
- **Mutating a detached entity expecting a write.** Changing a field on the `Appointment` returned
  from `reAssignAppointmentToAnotherDoctor` (now detached in the controller) produces no UPDATE.
- **Lazy access after detachment.** Calling `getDoctor().getName()` on that same detached
  `Appointment` throws `LazyInitializationException` — the reason nearly every other method maps to
  a DTO first.
- **Assuming `save()` always INSERTs.** For an entity with a non-null `@Id` (detached), `save()`
  MERGEs (UPDATE), not INSERTs.

## 11. Best Practices

- Map entities to DTOs **inside** the transaction and return the DTO, as this project does almost
  everywhere — it guarantees callers never receive a detached entity with live lazy proxies.
- Do all mutation while the entity is managed; never rely on changes made after the method returns.
- Prefer letting `orphanRemoval`/cascade drive removals (as in `disaccociateInsuranceFromPatient`)
  over manual `delete()` calls when the child's lifecycle is genuinely owned by the parent.
- Treat the `Appointment`-entity return in `reAssignAppointmentToAnotherDoctor` as the exception to
  study, not the pattern to copy.

## 12. Performance Notes

- Transient objects cost nothing until saved — build freely, save deliberately.
- Managed entities each carry a snapshot and participate in every flush's dirty-check scan; loading
  many entities you only read inflates that scan (prefer DTO projections for pure reads).
- `merge()` (the detached → managed path) can trigger an extra SELECT to load the current row before
  applying changes; staying within one transaction and using dirty checking avoids that round trip
  — which is exactly why the mutation methods here never round-trip through detached state.

## 13. Interview Questions

- **Q: Name the four entity states and one trigger for each transition.**
  A: Transient→Managed (`persist`/`save` of new), Managed→Detached (context close), Managed→Removed
  (`remove`/orphanRemoval), Detached→Managed (`merge`).
- **Q: Why does this project return DTOs instead of entities from services?**
  A: To avoid handing detached entities with lazy associations to non-transactional callers, which
  would risk `LazyInitializationException`; `reAssignAppointmentToAnotherDoctor` is the lone
  exception.
- **Q: Is `Appointment.builder().build()` persistent?**
  A: No — transient until `save()`.
- **Q: How does `orphanRemoval` relate to the Removed state?**
  A: Nulling an `orphanRemoval=true` association (e.g. `patient.setInsurance(null)`) moves the child
  to Removed, and flush emits the DELETE.

## 14. Summary

An entity moves through Transient → Managed → Detached (and Managed → Removed) as it interacts with
the persistence context. This project shows every state in real code: transient builders in
`createNewAppointment`/`onBoardNewDoctor`, managed entities driving dirty checking and cascades,
the removed `Insurance` in `disaccociateInsuranceFromPatient`, and the one detached-entity return in
`reAssignAppointmentToAnotherDoctor` that motivates the DTO-mapping discipline used everywhere else.
Knowing the current state tells you whether a mutation writes, whether a lazy field can load, and
whether `save()` inserts or merges.
