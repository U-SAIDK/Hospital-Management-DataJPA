# Query Methods (Derived Queries)

## 1. Definition

A derived query method is a repository method whose *name* is the query. Spring Data parses the
method name — `findBy` + field(s) + optional keywords (`Or`, `Between`, `Containing`, `OrderBy…Desc`)
— into a JPQL query at application startup, so you declare the signature and never write the query
body.

## 2. Core Idea

The method name is a tiny DSL. Spring Data's `PartTree` splits the name into a *subject* (`findBy`,
`existsBy`, `countBy`, `deleteBy`) and a *predicate* (the field/keyword chain). Each recognised token
maps to a piece of a `WHERE`/`ORDER BY` clause, and the method parameters bind positionally to the
predicate's placeholders in declaration order.

## 3. Why We Need It

Most queries are simple field lookups ("find the patient with this name", "find the user with this
username"). Writing `@Query("SELECT p FROM Patient p WHERE p.name = ?1")` for each is noise. Derived
methods let the signature carry the full intent — `Patient findByName(String name)` — with zero query
text, zero mapping, and compile-time-checked parameter types. They also fail fast: an unparseable or
non-existent-field name breaks the application *at startup*, not at first call.

## 4. Internal Working

1. At startup, for every repository method not inherited from `JpaRepository` and not annotated with
   `@Query`, Spring Data runs the name through `PartTree`.
2. `PartTree` strips the subject keyword (`findBy`), then tokenises the remainder against the entity's
   known properties and the reserved keyword grammar (`And`, `Or`, `Between`, `Containing`,
   `GreaterThan`, `OrderBy…Asc/Desc`, …).
3. It validates every referenced property against the entity metamodel — a typo like `findByNam`
   throws `PropertyReferenceException` at boot.
4. The parsed tree is turned into a JPQL query once and cached as the method's query plan. Method
   parameters are bound to the parts in order (`findByBirthDateOrEmail(birthDate, email)` → part
   `BirthDate` gets arg 1, part `Email` gets arg 2).
5. On each call the proxy executes the cached plan — no re-parsing, no reflection over the name per
   call.

## 5. Flow Diagram (ASCII)

```
 Method name:  findByNameContainingOrderByIdDesc(String query)
        │
        ▼  PartTree parsing (once, at startup)
 ┌───────────────────────────────────────────────┐
 │ subject   = findBy                             │
 │ predicate = Name + Containing                  │  → WHERE name LIKE %?1%
 │ order     = OrderBy Id Desc                    │  → ORDER BY id DESC
 └───────────────────────────────────────────────┘
        │
        ▼
 JPQL: SELECT p FROM Patient p WHERE p.name LIKE %?1% ORDER BY p.id DESC
        │   (cached as this method's query plan)
        ▼
 Each call: bind query → execute → List<Patient>
```

## 6. Real-world Analogy

Derived method names are like a well-designed search-URL scheme. `/patients?name-contains=jo&sort=id-desc`
tells you exactly what it returns without reading any handler code — the *path itself* is the query.
`findByNameContainingOrderByIdDesc` is the same idea in Java: the name is self-describing, and the
framework (like a router) translates it into the actual lookup.

## 7. How THIS PROJECT Uses It

`repository/PatientRepository.java` is the richest example, with four derived methods spanning the
grammar from trivial to near the readability ceiling:

- `Patient findByName(String name)` — single-field equality.
- `List<Patient> findByBirthDateOrEmail(LocalDate birthDate, String email)` — the `Or` combinator.
- `List<Patient> findByBirthDateBetween(LocalDate startDate, LocalDate endDate)` — the `Between`
  keyword (two parameters for one field).
- `List<Patient> findByNameContainingOrderByIdDesc(String query)` — `Containing` (LIKE) plus a sort.

`repository/UserRepository.java` shows two more, both returning `Optional`:

- `Optional<User> findByUsername(String username)` — used by `JwtAuthFilter` on every request and by
  `CustomUserDetailsService` during login.
- `Optional<User> findByProviderIdAndProviderType(String providerId, AuthProviderType providerType)`
  — the implicit `And` combinator; backs OAuth2 login and is the exact reason the
  `idx_provider_id_provider_type` composite index exists on `User`.

```java
List<Patient> findByBirthDateOrEmail(LocalDate birthDate, String email);

List<Patient> findByBirthDateBetween(LocalDate startDate, LocalDate endDate);

List<Patient> findByNameContainingOrderByIdDesc(String query);
```

```java
// repository/UserRepository.java
Optional<User> findByUsername(String username);

Optional<User> findByProviderIdAndProviderType(String providerId, AuthProviderType providerType);
```

## 9. Line-by-Line Explanation

- `findByName(String name)` — `findBy` + property `Name` → `WHERE p.name = ?1`. The single parameter
  binds to the single part. Returns a single `Patient` (or null) — safe only because `name` is not
  guaranteed unique here, so this is really "find one by name"; a duplicate would make the result
  nondeterministic (see Common Mistakes).
- `findByBirthDateOrEmail(LocalDate, String)` — the reserved word `Or` between `BirthDate` and
  `Email` produces `WHERE p.birthDate = ?1 OR p.email = ?2`. Parameters bind left-to-right to the two
  parts.
- `findByBirthDateBetween(LocalDate startDate, LocalDate endDate)` — the `Between` keyword consumes
  *two* parameters for the one `birthDate` field → `WHERE p.birthDate BETWEEN ?1 AND ?2`. This scan
  benefits from `idx_patient_birth_date`.
- `findByNameContainingOrderByIdDesc(String query)` — `Containing` becomes `WHERE p.name LIKE %?1%`
  (Spring Data adds the wildcards), and `OrderByIdDesc` appends `ORDER BY p.id DESC`. This is about as
  much as the naming grammar can carry before `@Query` becomes more readable.
- `findByUsername(String)` — `WHERE u.username = ?1`, returning `Optional<User>` so the caller must
  handle the not-found case; `JwtAuthFilter` relies on this every request.
- `findByProviderIdAndProviderType(String, AuthProviderType)` — the `And` combinator →
  `WHERE u.providerId = ?1 AND u.providerType = ?2`; the enum parameter binds as a value and, because
  `providerType` is `@Enumerated(STRING)`, matches on the stored string.

## 10. Common Mistakes

- **Returning a single entity from a non-unique field.** `findByName` returns one `Patient`, but the
  schema only forbids duplicate `(name, birthDate)` *pairs* — two patients can share a name. If two
  rows match, Spring Data throws a `NonUniqueResultException`. A `List<Patient>` return would be safer.
- **Typos in the method name.** `findByEmial` doesn't fail at compile time but throws
  `PropertyReferenceException` at startup — jarring if you don't know derived methods are validated
  against the entity metamodel.
- **Overloading the name past readability.** Long chains like
  `findByNameContainingAndBirthDateBetweenAndEmail…` become unreadable; the project deliberately stops
  at `findByNameContainingOrderByIdDesc` and switches to `@Query` for anything more complex.
- **Forgetting parameter order matters.** Parameters bind by position to the parsed parts, not by
  name — swapping the two args of `findByBirthDateOrEmail` would compile but query the wrong columns.

## 11. Best Practices

- Return `Optional<T>` for at-most-one lookups (as `UserRepository` does) and `List<T>` for
  potentially-many (as `PatientRepository` does for the `Or`/`Between`/`Containing` finders).
- Keep derived methods for genuinely simple predicates; once you need enums-in-JPQL, aggregation, or
  fetch joins, move to `@Query` — exactly the boundary this project draws between `PatientRepository`'s
  derived methods and its `@Query` methods.
- Name methods so the query is obvious to a reader who never sees the generated SQL — the whole value
  of the feature is self-documentation.
- Back range/lookup fields with an index (`idx_patient_birth_date` for the `Between` finder) so the
  derived query stays fast as data grows.

## 12. Performance Notes

- Name parsing happens once at startup via `PartTree`; each call just executes a cached query plan,
  so there is zero per-call reflection or string-parsing cost.
- `findByNameContainingOrderByIdDesc` generates a leading-wildcard `LIKE '%…%'`, which cannot use a
  standard B-tree index and forces a scan — acceptable for a learning project, but the reason
  full-text search or a trigram index would be used at scale.
- `findByProviderIdAndProviderType` is an index scan thanks to the composite
  `idx_provider_id_provider_type`; without that index it would be a full scan of `app_user` on every
  OAuth2 login.
- `findByBirthDateBetween` is a range scan that uses `idx_patient_birth_date`.

## 13. Interview Questions

- Q: How does Spring Data turn a method name into a query?
  A: The `PartTree` parser splits the name into subject + predicate, validates each property against
  the entity metamodel, and builds a JPQL query plan once at startup; parameters bind positionally.
- Q: When does a bad derived-method name fail?
  A: At application startup with `PropertyReferenceException`, not at first call — the names are
  validated against the entity's properties eagerly.
- Q: What's the difference between `findByBirthDateOrEmail` and `findByProviderIdAndProviderType`?
  A: `Or` produces a disjunction (`OR`), `And` a conjunction (`AND`); both consume one parameter per
  named field in declaration order.
- Q: Why return `Optional` from `findByUsername`?
  A: A username may not exist; `Optional` forces the caller (`JwtAuthFilter`,
  `CustomUserDetailsService`) to handle the absent case explicitly instead of risking a null.

## 14. Summary

Derived query methods make the method name the query. Spring Data's `PartTree` parses names like
`findByName`, `findByBirthDateOrEmail`, `findByBirthDateBetween`, and
`findByNameContainingOrderByIdDesc` (all in `PatientRepository`) plus `findByUsername` and
`findByProviderIdAndProviderType` (in `UserRepository`) into cached JPQL plans at startup — validating
every referenced field eagerly and binding parameters positionally. They cover the common simple
predicates with zero query text; the project switches to `@Query` exactly where the naming grammar
would stop being readable.
