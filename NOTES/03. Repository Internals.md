# Repository Internals

## 1. Definition

A Spring Data repository is a *pure interface* that extends `JpaRepository<Entity, Id>` and gets a
fully working implementation supplied at runtime — you never write the class. Internally, Spring
Data's `JpaRepositoryFactoryBean` builds a dynamic proxy backed by a single concrete class,
`SimpleJpaRepository`, which implements every inherited CRUD method against an injected
`EntityManager`.

## 2. Core Idea

`interface XRepository extends JpaRepository<X, Long> {}` is a *contract*, not code. At startup
Spring Data notices the interface, generates a proxy object that implements it, and registers that
proxy as a Spring bean. When a service calls `doctorRepository.findAll()`, the call lands on the
proxy, which routes inherited methods to a shared `SimpleJpaRepository` instance and custom
(`findBy…` / `@Query`) methods to a parsed-query executor.

## 3. Why We Need It

Every entity needs the same tedious CRUD: `save`, `findById`, `findAll`, `existsById`, `deleteById`,
`count`, plus pagination and sorting. Hand-writing an `EntityManager`-backed class for each of six
entities would be ~600 lines of identical boilerplate. Spring Data collapses all of it into one
declared interface per entity — in this project `DoctorRepository`, `AppointmentRepository`,
`DepartmentRepository`, and `InsuranceRepository` are *literally empty* (`{}`) yet fully functional,
because everything they need is inherited.

## 4. Internal Working

1. `@EnableJpaRepositories` (auto-applied by `spring-boot-starter-data-jpa`) scans the base package
   for interfaces extending `Repository`/`JpaRepository`.
2. For each one it registers a `JpaRepositoryFactoryBean`. At bean creation this factory:
   - Instantiates a `SimpleJpaRepository<T, ID>` — the concrete class that actually implements
     `save`, `findById`, `findAll`, `existsById`, `delete`, etc., all delegating to the injected
     `EntityManager`.
   - Creates a JDK dynamic proxy implementing your interface. The proxy's invocation handler
     inspects each called method:
     - inherited-from-`JpaRepository` → forwarded to the `SimpleJpaRepository` instance;
     - derived (`findByUsername`) → forwarded to a query built from the method name at startup;
     - `@Query`-annotated → forwarded to a JPQL/native query executor.
3. The proxy is registered as the bean that services autowire. `SimpleJpaRepository` is annotated
   `@Transactional(readOnly = true)` at the class level with write methods overriding to
   `@Transactional`, which is why a bare `save()` works even without a service-level transaction.

## 6. Real-world Analogy

The repository interface is a job description; `JpaRepositoryFactoryBean` is the staffing agency.
You post the description ("must be able to save, find, and delete Doctors"), and at startup the
agency instantly produces a fully trained temp worker (the proxy) who already knows how to do every
standard task by delegating to a shared expert (`SimpleJpaRepository`). You never interview or train
anyone — you just write the description and a qualified worker appears.

## 7. How THIS PROJECT Uses It

All six files under `repository/` are interfaces only — there is no hand-written implementation
class anywhere in `src/main/java`:

- `repository/DoctorRepository.java` — empty body `{}`.
- `repository/AppointmentRepository.java` — empty body `{}`.
- `repository/DepartmentRepository.java` — empty body `{}`.
- `repository/InsuranceRepository.java` — empty body `{}`.
- `repository/UserRepository.java` — two derived methods, no impl.
- `repository/PatientRepository.java` — derived + `@Query` methods, no impl.

The empty ones still provide full CRUD via inheritance, used at real call sites:

- `DoctorService.onBoardNewDoctor` — `userRepository.findById(...)`,
  `doctorRepository.existsById(...)`, `doctorRepository.save(doctor)`.
- `DoctorService.getAllDoctors` — `doctorRepository.findAll()`.
- `AppointmentService.createNewAppointment` — `patientRepository.findById(...)`,
  `doctorRepository.findById(...)`, `appointmentRepository.save(...)`.
- `AppointmentService.reAssignAppointmentToAnotherDoctor` — `appointmentRepository.findById(...)`,
  `doctorRepository.findById(...)`.
- `InsuranceService.assignInsuranceToPatient` / `disaccociateInsuranceFromPatient` —
  `patientRepository.findById(...)`.

Every one of those methods is inherited from `JpaRepository` — none are declared in the interfaces.

## 8. Code Example From This Project

```java
// repository/DoctorRepository.java  — entire file, no implementation class exists
public interface DoctorRepository extends JpaRepository<Doctor, Long> {
}
```

```java
// service/DoctorService.java
@Transactional
public DoctorResponseDto onBoardNewDoctor(OnboardDoctorRequestDto onBoardDoctorRequestDto) {
    User user = userRepository.findById(onBoardDoctorRequestDto.getUserId()).orElseThrow();

    if(doctorRepository.existsById(onBoardDoctorRequestDto.getUserId())) {
        throw new IllegalArgumentException("Already a doctor");
    }

    Doctor doctor = Doctor.builder()
            .name(onBoardDoctorRequestDto.getName())
            .specialization(onBoardDoctorRequestDto.getSpecialization())
            .user(user)
            .build();

    user.getRoles().add(RoleType.DOCTOR);

    return modelMapper.map(doctorRepository.save(doctor), DoctorResponseDto.class);
}
```

## 9. Line-by-Line Explanation

- `public interface DoctorRepository extends JpaRepository<Doctor, Long> {}` — the type parameters
  tell the factory the entity (`Doctor`) and id type (`Long`); the empty body means every method
  used below is inherited and implemented by `SimpleJpaRepository` via the proxy.
- `userRepository.findById(...)` — inherited; returns `Optional<User>`, resolved by
  `SimpleJpaRepository.findById` calling `EntityManager.find`. `.orElseThrow()` converts a missing
  row into an exception.
- `doctorRepository.existsById(...)` — inherited; `SimpleJpaRepository` issues a lightweight
  `SELECT count/… WHERE id = ?` rather than loading the entity, so it is cheaper than `findById`
  when you only need a yes/no.
- `doctorRepository.save(doctor)` — inherited; `SimpleJpaRepository.save` checks whether the entity
  is new (here `Doctor` uses a shared PK via `@MapsId` on `user`, so newness is inferred from state)
  and calls `persist` for an INSERT or `merge` otherwise.
- The whole method being `@Transactional` means all these proxy calls share one persistence context,
  which is also why `user.getRoles().add(...)` persists by dirty checking without a `userRepository.save(user)`.

## 10. Common Mistakes

- **Looking for the implementation class.** New readers hunt for `DoctorRepositoryImpl` — it does
  not exist and is not supposed to; the proxy is generated at runtime.
- **Adding `@Repository` to the interface expecting it to "activate" it.** It is unnecessary; Spring
  Data registers the proxy purely from the interface extending `JpaRepository`. (None of this
  project's repositories are annotated `@Repository`.)
- **Assuming an empty repository is unfinished.** `AppointmentRepository {}` is complete —
  Appointments are created/updated through managed entities and inherited `save`/`findById`, so no
  custom methods are needed.
- **Calling `save()` and expecting it to always UPDATE (or always INSERT).** `SimpleJpaRepository.save`
  decides between persist/merge based on entity state; misjudging that leads to surprise inserts of
  detached entities.

## 11. Best Practices

- Keep repositories as thin interfaces with no business logic — this project's repositories contain
  only query declarations; all rules (e.g. the "already a doctor" check) live in the service layer.
- Prefer `existsById` over `findById(...).isPresent()` when you only need existence — the project
  does exactly this in `onBoardNewDoctor` to avoid materializing the entity.
- Let inheritance do the work: leave a repository empty (`{}`) until a real query need appears rather
  than pre-adding speculative methods.
- Return `Optional<T>` from finders (as `findById` does) so callers must handle the missing case
  explicitly — the services here pair it with `.orElseThrow(...)`.

## 12. Performance Notes

- The proxy indirection (interface → dynamic proxy → `SimpleJpaRepository`) adds negligible per-call
  overhead; the dominant cost is always the SQL round trip, not the Spring Data layer.
- `existsById` is cheaper than `findById` because it avoids loading and mapping the full entity — a
  meaningful saving on wide rows, and the reason `onBoardNewDoctor` uses it for the duplicate check.
- Because `SimpleJpaRepository` methods are transactional, calling a bare `save()`/`findById()`
  outside a service transaction still works but opens and closes a short transaction each time;
  grouping related calls under one `@Transactional` service method (as here) is both correct and
  cheaper.

## 13. Interview Questions

- Q: Where is the implementation of an empty repository interface?
  A: Generated at runtime by `JpaRepositoryFactoryBean` as a JDK dynamic proxy backed by
  `SimpleJpaRepository`; no source class exists.
- Q: What does `SimpleJpaRepository` do?
  A: It is Spring Data JPA's single concrete implementation of the CRUD/pagination contract, working
  entirely through an injected `EntityManager`.
- Q: Do you need `@Repository` on the interface?
  A: No — extending `JpaRepository` is enough for Spring Data to register the proxy bean. (Optional
  exception translation aside, this project doesn't use it.)
- Q: How does `save()` know whether to INSERT or UPDATE?
  A: `SimpleJpaRepository.save` checks whether the entity is new and calls `EntityManager.persist`
  (INSERT) or `merge` (UPDATE) accordingly.

## 14. Summary

A Spring Data repository is a declared interface, not a written class. At startup
`JpaRepositoryFactoryBean` builds a dynamic proxy backed by `SimpleJpaRepository` and registers it as
the bean services autowire. All six repositories in this project are interfaces only — four are
completely empty yet fully functional through inherited CRUD, exercised at real call sites like
`DoctorService.onBoardNewDoctor` (`findById`, `existsById`, `save`) and throughout
`AppointmentService`/`InsuranceService`. Business logic stays in the services; the repositories stay
pure data-access contracts.
